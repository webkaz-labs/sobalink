# ネイティブ UI 試作の実機試験手順

この文書は試作 UI の**試験方法**です。実機での合格結果ではありません。
最初の対象は **Windows x64 と macOS ARM64（Apple Silicon）** です。
macOS Intel、Windows ARM64、署名付きインストーラーの対応・動作は主張しません。
本体と別のクライアントであり、通常版 UI の置き換えではありません。隔離した試験専用で、日常利用の代替として使わないでください。

この手順を作成した統合段階では、PR #66 を含む main `64a92eeb` を土台に、PR #67 のネイティブ UI を取り込む準備をしていました。公開版・最終ソース SHA・合格結果は、対象リリースの記録を確認してください。この文書だけでは確定しません。

**過去のキットとの区別:** 以前の未署名実機試験キットは PR #67 系統を対象とし、PR #66 を含まないものでした。その manifest（配布物の一覧と情報）と SHA-256（ファイル内容の照合値）は、そのキットだけの履歴です。過去のキットを今回のリリース資産として使ったり、その結果を新しいソースの合格に読み替えたりしません。

資料は同じソースの文書を参照します。配布物に資料が含まれない場合は、対象リリースの正確なコミットのオンライン資料を参照してください。

## 0. 安全な準備

- 自分で試験を許可できる端末だけを使用します。端末・ネットワークの管理方針に従ってください。
- 配布物の署名・来歴（どのソースからどうビルドしたか）の検証と、OS 向けの発行者署名・公証は別です。配布署名の成功だけでOS署名済みとは扱いません。過去の未署名キットはリリース資産ではありません。macOS のリンク時の ad-hoc 署名（発行者を証明しない署名）があっても、発行者の認証を意味しません。
- OS、管理者、保護ソフトが実行を止めた場合は**そこで中止**し、ブロックを記録します。署名検査、Gatekeeper、SmartScreen、隔離属性、ウイルス対策を無効化・除去して回避しません。管理者権限での再実行も行いません。
- 配布元のコミット、対象 OS/CPU、バイナリ名、提示された SHA-256 を確認します。ハッシュ一致は署名や実機検証の代わりではありません。提示されたハッシュがなければ、出所確認済みとは記録しません。
- 既存の通常利用プロファイルを使わず、今回だけの新しい専用フォルダーと架空の表示名を使います。既存プロファイルのコピー、移行、上書き、削除はしません。
- 写真、既存文書、認証情報、アドレス帳等は試験に使いません。画面・ログ・ファイルには実際の端末名、アカウント名、所属、パス、接続先が現れる場合があります。共有する結果は一般的なラベルに置き換え、個人や利用環境を特定・推測できる情報が残らないことを確認します。未確認なら共有を止め、対象箇所と理由だけを伝えます。
- 起動・送信・受信・停止は各段階で人が確認します。以下をまとめて自動実行するスクリプトは作成しません。ログイン項目や自動起動も登録しません。

対象リリースの配布形式と検証手順を確認し、新しい専用フォルダーで試験します。以下は実行ファイルのあるフォルダーをターミナルで開いた場合の例です。
Windows の実行ファイルは `soba-native.exe` と `soba.exe`、macOS ARM64 は `soba-native` と `soba` です。`SHA256SUMS` と対象の manifest で対象・出所を照合し、公開配布物は [配布の検証手順](../../docs/DISTRIBUTION.md) に従って署名・来歴も確認します。本体はUIと同じソースの対象配布物を使い、PATH上の別版に置き換えません。

`TEST_PROFILE_DIRECTORY` は自分で選んだ試験専用の絶対パスに置き換える説明用表記です。実ユーザーのパスはこの文書に含めていません。
後半の `sh` ブロックは macOS 用です。Windows PowerShell では `./soba` を `& .\soba.exe`、`./soba-native` を `& .\soba-native.exe` に読み替え、以降の引数はそのまま使います。バイナリを直接使う場合、Go のインストールは不要です。

## 1. 通信しないデモから開始

Windows PowerShell:

```powershell
& .\soba-native.exe --demo --tray --locale auto
```

macOS:

```sh
./soba-native --demo --tray --locale auto
```

デモは架空データです。メッセージ・ファイル操作もシミュレーションであり、実送受信や OS ファイル選択の合格には数えません。

1. トレイ／メニューバーのアイコンを押し、OSロケールに応じたパネルが開くことを確認します。初期状態でパネルが隠れていることは異常ではありません。
2. アイコンの再クリック、「隠す」、閉じる、入力欄等に消費されない Escape で隠れ、再表示できることを確認します。右クリックでもパネルを開けるか確認します。
3. 架空の許可済み端末を選び、メッセージ下書きを入力します。隠す→再表示で下書きが残ることを確認します。
4. 別のアプリへのフォーカス移動や IME 候補表示でパネルが勝手に閉じないことを確認します。通常の「フォーカスを失えば隠れる」仕様ではありません。
5. 「UIを終了（本体は継続）」でアイコンと UI プロセスが終了することを確認します。再起動後は下書きが復元されないことを確認します。デモでは本体は起動されません。
6. トレイを作成できない場合、通常ウィンドウへのフォールバックと案内を確認します。これはトレイ試験の合格ではありません。フォールバックではウィンドウを閉じると UI が終了します。

日本語を明示する場合は `--demo --tray --locale ja`、英語は `--locale en` を使います。通常ウィンドウも `--demo --locale ja`（`--tray` なし）で別途確認できます。

### 日本語入力・キーボード・読み上げ

IME は、かなを漢字などに変換する日本語入力機能です。

- 下書きに `試験です。「こんにちは」、次の行へ。`、改行、`全角ＡＢＣ１２３`、絵文字を入力します。かな変換、候補選択、変換の取消、Backspace、カーソル移動、選択、貼り付けを確認します。
- 変換確定の Enter だけで送信されないこと、未確定文字と候補ウィンドウの位置が妥当なことを確認します。
- Tab / Shift+Tab で移動でき、フォーカスが見えることを確認します。端末行は Enter / Space で開閉し、送信前確認、戻る、確定にキーボードで到達できるか確認します。
- Windows の Narrator、macOS の VoiceOver で、端末名、ボタン、開閉状態、入力欄ラベル、確認内容、状態変化が理解できるか確認します。コードに役割があることだけでは合格にしません。読めない項目・順序・フォーカスの問題を個別に記録します。
- 日英切替で説明・確認・状態表示が揃って変わり、入力文字が翻訳・消失しないか確認します。別起動で `--locale auto` と `--locale en` も確認し、OS ロケールと結果を記録します。

### 画面の拡大率（DPI）・配置

- 利用可能な Windows の 100% / 150% / 200%、macOS の標準／拡大表示で文字欠け、スクロール、クリック位置、候補表示を確認します。使えない倍率は未実施とします。
- 複数画面があれば、異なる倍率の画面、端・下側のタスクバー／メニューバーで開き、パネルが作業領域内に収まるか確認します。Windows の隠れたアイコン領域も確認します。
- 通常ウィンドウを最小サイズ付近にして確認します。トレイパネルは固定サイズで、通常ウィンドウのリサイズ試験とは別です。
- 明暗の外観、拡大表示でアイコンと文字が読めるか確認します。OS のウィンドウを開かずに描画した PNG はこれらの実機結果の代用になりません。

## 2. 専用の本体プロファイルを用意し、読み取り専用で接続

本体の準備は試作 UI とは別です。[案内付き CLI](../../docs/CLI_GUIDE.ja.md)と[利用ガイド](../../docs/GENERIC.ja.md)に記載された操作を使います。
以下の例は macOS 用です。Windows では冒頭の説明どおり、同梱の `.exe` を PowerShell の `&` で呼び出します。

1. 通常データとは別に、今回だけの未使用フォルダーを選びます。既存データが入っている、目的が不明、アクセスが拒否される場合は中止します。
2. 各コマンドを一つずつ実行し、毎回同じ専用パスであることを確認します。

```sh
./soba --state-dir "TEST_PROFILE_DIRECTORY" init --name example-node
./soba --state-dir "TEST_PROFILE_DIRECTORY" start --offline --background
./soba --state-dir "TEST_PROFILE_DIRECTORY" status
```

`init` はローカル初期化です。ここでは参加登録・認証・ネットワーク接続を行いません。起動がタイムアウトした場合も、プロセスが動いている可能性があります。再起動を繰り返さず同じプロファイルの状態を確認してください。

3. デモの UI を終了し、今作った本体プロファイルを明示して読み取り専用で開きます。

```sh
./soba-native --state-dir "TEST_PROFILE_DIRECTORY" --tray --locale ja
```

4. 起動直後に勝手に状態を取得しないこと、「状態を取得」で本体を読めることを確認します。Windows は実際の named pipe（同じ端末内の通信経路）、macOS は実際のローカル IPC（プロセス間通信）の試験です。
5. オフライン・相手なしの表示と、IPC 読取成功を混同していないことを確認します。送信・受信操作は無効であることを確認します。
6. 「状態を取得」を続けて押しても重複した取得を開始しないことを確認します。
7. UI 終了後も、同じプロファイルの本体 `status` が読めることを確認します。UI 終了は本体停止ではありません。

設定確認が必要なら、同じ本体・同じプロファイルで次を明示的に実行します。Web UI のログイン URL やコードは共有・撮影しません。

```sh
./soba --state-dir "TEST_PROFILE_DIRECTORY" ui
```

## 3. 両者が同意した場合だけ、実送受信へ進む

この段階は任意です。デモだけで終えて構いません。

- 両参加者が使用端末、試験用ネットワーク、相手、送る内容、受信先を了解していることが前提です。もう一方にも専用プロファイルと架空の表示名（例: `example-peer`）を用意します。実際の接続相手を架空にするという意味ではなく、試験用の端末を非個人的な名前で区別します。
- 既存の Web UI と[接続セットアップ](../../docs/CONNECTION_SETUP.ja.md)で、選んだ試験構成だけを明示的に準備します。自動参加、通常プロファイルからの認証情報コピー、ネットワーク制限の回避はしません。必要な許可が得られなければ中止します。
- 相手の識別情報を双方で照合し、文字・ファイルの許可を既存 UI で明示的に設定します。接続許可と文字・ファイルの信頼は別です。自動受信を使わず、受信確認を試せる構成を選びます。
- 試作 UI で対象が**許可済み・一時停止していない**ことを確認し、正確な相手を選びます。無効な場合は試作 UI から許可や一時停止を勝手に変更できません。理由を解決するか試験を止めます。

読み取り専用 UI を終了してから、両側でそれぞれの専用パスを指定し、明示的に送受信操作を有効化します。

```sh
./soba-native --state-dir "TEST_PROFILE_DIRECTORY" --tray --locale ja --enable-send
```

### メッセージ

1. 状態を更新し、対象端末のやり取り画面を開きます。
2. 試験文 `試験です。「こんにちは」、受信確認をお願いします。` を入力します。「送信内容を確認」で送信先の名前・ID・全文を確認します。
3. 一度「下書きに戻る」を試し、未送信で編集できることを確認します。隠す→再表示でも宛先と本文が混ざらないか確認します。
4. 再確認後「メッセージ送信を確定」を一度だけ押します。要求中に連打して重複送信できないことを確認します。
5. 両側で履歴を更新し、受信側の本文が一致し、一件だけ到着したことを参加者が確認します。「要求が完了」「送信済み」の表示だけで到達合格にしません。履歴は最新6件の表示で、全履歴ブラウザーではありません。

### 小さなファイル

1. 新しい試験用フォルダーに、内容が `native-poc-test` のみの小さな `sample.txt` を手動で作ります。元からあるファイルやフォルダー全体は選びません。
2. 送信側で「ファイルを選択…」を開き、一度キャンセルします。パネルが勝手に消えないこと、送信準備が残らないことを確認します。
3. 改めてファイルを選び、確認画面の相手 ID、ファイル名／パス、サイズ、合計を照合します。一度「破棄」を試し、受信が始まらないことを確認します。
4. 再度選択して確認後「送信を確定」を一度だけ押します。確認後にファイルを編集したり、別の相手に切り替えて流用したりしません。
5. 受信側の履歴を更新し、「受信を確認」で送信元・転送・内容を照合します。「保存先を選択…」で今回だけの専用受信フォルダーを選び、表示を確認して「受信を確定」を押します。受信先の選択前に確定できないことも確認します。
6. 両側の状態を更新し、完了状態・バイト数と、実際に保存されたファイルのサイズ・SHA-256 が送信元と一致することを確認します。UI はハッシュを表示する検証器ではないため、OS の機能で両方を計算します。受信ファイルは自動で開きません。
7. 別の新しい試験転送で「辞退を確認」→「戻る」と、改めて「辞退を確定」を試します。辞退後にファイルが保存されていないことを確認します。前の結果が不明ならこの試験に進みません。

SHA-256 の計算例（`TEST_FILE` は確認対象の試験ファイルだけを指定）:

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath "TEST_FILE"
```

```sh
shasum -a 256 "TEST_FILE"
```

ハッシュは送信元と保存先の実ファイル同士を比較します。改行形式を含め同じバイト列であることが必要です。

### 中断・失敗時

- 通信エラーは未到着の証拠ではありません。結果不明なら**再送せず**、履歴・状態・受信者の記録を確認します。ファイルでは「準備状態を確認」も使えますが、結果不明の操作のロック解除や再送許可ではありません。
- UI の再起動、別ウィンドウ、別 ID によってロックを回避しません。要求の受付と配送完了を区別し、判断できなければ「結果不明」のまま試験を止めます。
- 切断・スリープ復帰を試すなら、まず送受信が残っていない段階で行います。再取得前の古い状態を成功扱いしないこと、取得失敗時に古いデータが消えることを確認します。制限を回避するネットワーク設定変更は行いません。
- 送信中の強制終了等はこの最小試験では要求しません。実際に発生した場合は再送せず、双方の状態を確認します。

## 4. 終了と安全な片付け

1. 結果不明の操作、未確定の受信、進行中の転送がないか双方で確認します。未解決ならデータを保全し、正常完了とは記録しません。
2. 試作 UI の「UIを終了（本体は継続）」を押します。隠すだけでは終了ではありません。
3. 今回自分が開始した専用本体だけを、正確な専用プロファイル指定で明示的に停止します。

```sh
./soba --state-dir "TEST_PROFILE_DIRECTORY" stop
```

4. 停止要求の受付はプロセス終了の証明ではありません。OS のプロセス表示などで対象本体の終了と、そのプロファイルの IPC 終了を確認します。IPC が消えただけで断定せず、曖昧なら状態を保持します。無関係なプロセスを強制終了しません。
5. 通常プロファイルや他の本体は停止・削除しません。この文書は自動削除を行いません。試験フォルダーを片付ける場合も、今回作ったものだけか、必要な証跡が残っているかを人が確認してから行います。

## 5. 結果の記録

各項目を **合格／不合格／未実施／ブロック／結果不明** で記録します。

- コミット、ビルド対象、バイナリ SHA-256、OS バージョン、CPU アーキテクチャ。
- デモ、トレイ、通常ウィンドウ、読み取り専用 IPC、明示送信をそれぞれ分ける。
- IME、読み上げ製品・バージョン、DPI、画面配置、再現手順、期待と実際。
- 本文一致、受信件数、転送の完了記録、両ファイルのサイズと SHA-256 の一致。
- UI 終了、本体の継続、本体の明示停止・終了確認を別々に記録する。
- 操作時間・待機 CPU・メモリを測った場合は条件と値を記録し、測っていなければ未実施とする。

実データの画面・ログをそのまま添付しません。必要な不具合は可能ならデモで再現し、一般化した記録だけを共有します。クロスビルド、自動テスト、OS のウィンドウを開かない描画の成功を、この実機試験の合格に読み替えないでください。
