# 近くの端末との接続セットアップ

[English](CONNECTION_SETUP.en.md) · [セキュリティ境界](SECURITY.ja.md)

近くの端末との接続では、範囲を明示した「相手を選んで依頼→相手が承認」と、任意の指紋全文照合を提供します。探索の名前や接続先は本人確認の証拠ではありません。初回に受け入れた鍵を記憶する方式（TOFU）は、最初の交換時の能動的ななりすましを防げません。アプリの権限は別途許可します。

これはソース開発段階です。決定的テスト、隔離 loopback 検証、配布物の検証、実端末検証は別の確認段階であり、互いの代替にはなりません。この文書は実端末や公開済みバイナリでの合格を主張しません。

## 依頼して承認する手順（v2）

1. 受付側で「接続依頼を受け付ける」を選び、ネットワーク範囲と接続待受・中継の正確な接続先を許可します。開始前に確認時間を120〜1200秒から選べます。
2. 依頼側で「相手を選んで依頼」または「接続の開始のみ」を選びます。後者はLAN待受も探索用ソケットも作りません。受付側を選ぶか、相手の受付画面の数値IP:ポートを入力します。
3. 正確な相手の鍵、相手の範囲、中継の接続先・証明書、有効期限を確認して依頼します。確認方式は双方で一致する必要があります。
4. 受付側で固定された依頼内容を確認し、承認または拒否します。独立した指紋全文照合を選んだ場合は双方の照合・承認が必要です。TOFU方式ではコードやPNGの転送は不要です。
5. ペアの保存、通信の確認、アプリの権限を別々に確認します。結果が不明なときは元のセッションを照会し、代わりの依頼を重ねません。

相手の期限が短ければ短い方が適用されます。確認時間を長くしても探索は120秒で終わります。選択済みの依頼は有効期限まで続き、セッション中は接続先の手入力も使えます。期限切れ後は新しい依頼と許可が必要です。照合済みの鍵を無言でTOFUへ格下げせず、解除済みの鍵を遅れた依頼で復元しません。

`soba nearby` で案内付き操作を使えます。明示的なコマンドは `soba nearby --help` を参照してください。画面のない環境でも正確なセッション・依頼・版の指定と明示的な許可が必要です。`--json` は質問も自動承認も行いません。`x` は継続したまま案内を終了し、`q` は取消を要求して終了処理を確認します。画面を閉じることとペアの解除は別です。

手入力は選択範囲内の数値のプライベートIPv4またはIPv6 ULAに限ります。DNS、転送先URL、link-local・zone指定、公開アドレス、サブネット走査は補助動線にしません。探索で見つかっても接続できないことがあります。双方が新規着信を受け付けられない場合、直接LANでの初回接続は成立しません。中継アカウントの作成やファイアウォール設定変更は行いません。接続の開始のみでもローカル管理用IPCは必要で、loopback待受まで禁止する環境は別の未検証条件です。

## 解除した鍵を再登録する

解除した鍵は、新たな依頼を受け取るだけでは再登録できません。補助操作の「解除した端末」、またはCLIの `nearby revoked` で、正確な鍵・世代・以前の確認方式を確認します。再登録の許可にはオフライン状態で、稼働中のネットワーク、未終了の接続設定、その鍵の保存済み通信ペアがないことが必要です。案内に従い同じプロファイルを停止してオフラインで再起動してください。この操作では進行中の転送や接続が終了します。

`nearby reenroll --peer-key KEY --generation N --consent` は、その解除世代の正確な鍵について新しいペアリングを試すことだけを許可します。古いペア、アプリの信頼、自動保存、サービスは復元しません。その後、改めて許可して新しい依頼を始めます。以前に独立した全文照合を済ませた鍵は、引き続き全文照合が必要です。再登録後に古いセッションや保存処理が再び有効になることはありません。

応答が失われたときは、解除した鍵の状態を再照会してください。一覧から消えただけではどの操作が完了したか断定できません。確認せず繰り返したり、非公開の状態ファイルを編集して解除記録を消したりしないでください。同じ表示名でも同一端末とは限りません。既に確認した接続先の鍵が変われば、その確認は無効です。

## 明示的な従来の指紋全文照合（v1）

以下の小節は、セッションの上限が120秒のv1を説明します。v2は上の「依頼して承認する手順」を使い、開始前に120〜1200秒から選びます。相手の期限が早ければ、そちらを優先します。

1. 両方の端末で接続画面を開きます。表示名と現在のネットワーク範囲を選び、短時間の広告と正確な bootstrap 待受端点を許可します。この端末を中継に使うことを許可するか、相手を中継に使うかを明示的に選びます。初期選択はありません。新しい接続では少なくとも片方で中継を許可し、別の高位ポートを指定してください。中継できる条件や到達性は後で確認し、この選択だけで保証しません。すでに別のホスト経由で接続中の端末は、承認済みのホストを維持します。
2. 両方で相手を選びます。multicast 探索が使えない場合は、現在のセットアップ接続情報をコピーまたは QR で交換します。読取りだけでは承認せず、任意の探索も始めません。
3. 接続計画を確認します。双方の identity、選出した host、正確な中継 address と certificate pin、各端末の範囲を表示します。LAN backend はローカルで選んだ prefix の strict allowed-LAN-destinations policy を使い、その範囲への UDP/TCP を許可します。物理 interface の隔離やプロセス全体の通信封じ込めを意味しません。
4. 相手の画面の照合 QR またはコピーした全文が一致することを確認します。手動なら 64 文字の fingerprint 全体を照合します。一部の文字、数桁、色、表示名だけで判断しません。両端でそれぞれ承認します。
5. 相互の認証済み protocol 応答を待ちます。設定済み・ペア済み・接続済みは別の状態です。メッセージやファイルの申出を受ける信頼は別途許可します。

未検証の第三者が示した QR や、同じ未検証ネットワーク経由で単に返された照合値は相手の確認になりません。相手端末の画面、または別途確認済みの経路で交換します。

### CLI の最短手順と修正

新しいプロファイルでは、両端末で実行します。

```sh
soba init
soba start --offline --background
soba nearby --legacy-interactive
```

別のプロファイルを使う場合は、すべてのコマンドで同じ `--state-dir DIR` を指定してください。すでに起動中でオフライン再起動が必要な場合は、先に明示的に停止します。実行中の転送と接続も停止します。プロファイルの置換や消去は行いません。

表示名を入力し、ネットワーク範囲を確認して、`y` でこの端末の中継を許可するか、`n` で相手を中継に使うかを選びます。その後、表示された待受を別途承認します。空欄や不明な回答では再度質問し、何も許可しません。最終確認の `p` でセットアップ・中継用ポートを編集、`b` で入力全体を編集、`q` で取消できます。ポートの編集だけでは通信せず、新しい正確な待受を表示して改めて承認します。1024〜65535から54543〜54545とローカル管理用を除く、重複しないポートを選んでください。利用可能かは開始時に確認し、無言で別のポートへ変更しません。

稼働中の CLI の操作質問では、`r` または Enter で元のセッションを更新し、`m` で相手の連絡先を貼り付け、`v` で表示された計画を照合・承認します。`x` はセットアップを元の期限まで動かしたまま案内を終了します。操作質問での `q` や入力終了は取消を要求し、終了処理を待ちます。連絡先・指紋の入力中の `q` は操作質問へ戻ります。プロセスの中断や応答の消失だけでは停止を確認できません。同じプロファイルの `soba nearby status`（ID が分かる場合は `--session ID`）で照会し、確認せずに `start` を繰り返さないでください。

許可され、到達可能な中継役が見つからなくても、原因は推測しません。両方で許可しなかった場合は、終了処理の確認後、Web の「中継役の許可を見直して再試行」、または CLI の新しい確認への質問で進みます。両端末で表示名・範囲・役割を改めて許可して新しいセッションを開始し、許可された片方を中継に使ってください。以前の照合・承認は引き継ぎません。この中継役不在の失敗が未確定保存を伴わず、すべての一時的な処理の終了を確認した場合だけ、再確認できます。復旧・保存済みネットワーク・中継先競合は別途確認が必要なままです。既存の接続では承認済みのホストを維持します。

Web は QR を表示し、ローカルの PNG 画像から QR の文字列を読み取れます。カメラスキャナーや QR ダウンロードボタンはありません。連絡先・指紋の全文コピーも使えます。CLI の案内は文字入力です。端末への QR 表示は `nearby status --qr`、`nearby contact --session ID --qr`、`nearby verification --session ID --qr` で選べます。CLI が読み込み・保存するのは文字列で、PNG ではありません。

両端末の承認後は、保存した LAN 接続と選択した中継が120秒のセットアップ後も継続できます。現在の接続と待受を停止するには、Web のネットワーク操作「sobalink を停止」、または同じプロファイルの `soba stop` を使います。実行中の転送も停止しますが、保存済みのペアは解除されません。セットアップの取消では一時的なセットアップだけを終了します。

### 許可とライフサイクル

- セッションは最大120秒です。Linux と Windows は同じ広告の新しい受信で候補の有効期限を更新します。macOS は選択 interface のシステム DNS-SD query を使い、正確な query の継続中は cache の候補を表示する場合があります。最近の通信や到達性の証明ではありません。削除、query 失敗、範囲変更、取消、期限切れで元の選択は無効になります。候補によるセットアップ期限の延長や失効 ID の復活はありません。両側承認後は検証済みの正確な transcript だけを元の期限まで固定します。相手を確認できなくなった場合は古いセットアップを取り消し、終了確認後に両端末で同意と照合をやり直します。観測の違いは [macOS API の範囲](../internal/nearby/DNSSD.ja.md) を参照してください。
- 探索広告は選んだ alias、ランダム session ID、protocol/capability、bootstrap 端点だけです。恒久 identity、招待、ファイル名、サービス一覧、OS hostname は広告しません。
- bootstrap はローカルで選択済みの相手 session と正確な source/address 範囲だけを受け付けます。受信だけで相手を選択したり、未選択の端点へ callback したりしません。
- 両端の鍵と session ID、alias、公開 scope、session ごとに無作為生成したローカル許可 revision、役割、端点、正確な pin、計画 revision、期限を全文 transcript に結びます。interface 名・hardware の確認情報はローカルに留めます。
- 画面間の照合前に暗号化 proof が証明するのは、自己申告された選択鍵の保有だけです。表示名の人物を認証しません。全文 SHA-256 の照合を使い、攻撃者の鍵選別に弱い未レビューの短い照合コードを導入しません。
- session 順で固定した coordinator が、認証済みの方向別観測から一度だけ host を選びます。互換性のある既存 host を優先し、同条件なら session 順で決定します。失敗した方向は利用不可または不明のままで、FW・sleep 等の原因を推測しません。
- 重複した承認・通信は同じ計画と招待を使います。相手、範囲、役割、端点、証明書の変更は取消と新規 session・再承認を必要とします。
- 相互の接続確認後は探索広告を停止します。正確な session の最終応答のため、bootstrap 待受だけが元の120秒期限まで残る場合があります。再招待や期限延長はせず、明示取消ではこの待受も終了します。
- 取消・期限切れでは所有する探索と bootstrap を閉じ、未使用招待を取り消します。ペア保存が既に起きた可能性があれば復旧が必要と表示し、rollback を主張しません。終了を確認できない所有 resource は復旧の制限を保持します。
- 承認した LAN 設定とペアは今後の利用に向けて保存します。成功後の backend と選択した host 待受は短時間の setup が終わっても停止まで継続します。停止しても保存済みペアの取消にはなりません。
- 別の端末への接続は明示的に新しく始めます。残っている setup の最終応答待受を閉じ、終了確認後の `nextAction: start_new_setup` を待ちます。以前の接続結果と稼働中 LAN backend は残り、新しい画面・session では範囲、役割、照合を改めて承認します。
- 新規 LAN backend は相互成功までセットアップが所有します。取消で、借用した既存 backend を閉じることはありません。

### 既存接続と再起動

既存の認証済み接続は通常の相手操作から利用できます。使うだけなら新しいセットアップは不要です。実行中の LAN host または relay client は、strict な単一 prefix と既存の正確な中継 anchor が計画に一致する場合だけ借用できます。client は新しい host 役を要求せず、相手が同じ既存 anchor のローカル host を提示する必要があります。外部 relay を使う client 同士から新しい host を作りません。

互換性のない保存済みペア、準備済み経路、未確認の起動・アプリ権限は従来のネットワーク設定で確認します。探索の許可でリセットや再開はしません。別の process-scoped backend、終了未確認の所有者、identity 変更は、新しい通信を始める前に停止・再起動または復旧状態になります。同じ profile を offline で開き直して、新しい session を作成します。古い照合結果・承認を再起動後へ引き継がず、TCP や backend の無停止移行を約束しません。

OS の FW、route、ネットワークセキュリティ、router、特権サービスを変更しません。QR 交換は通信制限を解除しません。許可済みで到達可能な host がない場合は、既存の承認済み接続または詳細設定を使います。

### ローカル command 契約

Web と CLI は同じ Core 契約を使います。

- `setup.scopes {}`: 現在のローカル候補と不透明な `scopeId` を読み取る
- `setup.start`: alias、`scopeId`、bootstrap port、host 役と relay port、明示 consent
- `setup.status`: 公開状態、接続情報 text/QR、計画照合。招待を含めない
- `setup.select`: 現在の候補 ID を一つ選ぶ
- `setup.manual`: 制限付きの正規接続情報 text から同じ確認へ進む
- `setup.approve`: 正確な session ID、計画 revision、全文 fingerprint、ローカルでの明示確認
- `setup.cancel`: 正確な session を停止し、取消と復旧必要を区別する

接続情報は `sobalink-setup-contact-v1:` と正規 base64url JSON、照合情報は `sobalink-setup-verify-v1:` と全文 SHA-256 digest です。どちらもアプリ信頼の許可や再利用可能な capability ではありません。

開始応答が不明な場合の `setup.status {}` は、その process の現在 session を読むだけです。特定の client が作成・占有した証明にはなりません。以前の session ID を拒否し、指定した公開 contact・範囲を確認して古い承認を消し、現在の計画全文を再確認してから承認します。他の認証済みローカル client も同じ Core を操作できます。
