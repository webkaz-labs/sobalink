# 相手1台の転送設定を参照する

[English](RESOURCE_INSPECTION.en.md)

このソース版では、管理対象の DirectLAN の相手1台に、転送設定の2項目と実効値の参照を許可できます。この参照のみの範囲では、一覧・操作履歴・任意のコマンド・遠隔での変更操作は公開しません。別途確認する[管理許可](RESOURCE_MANAGEMENT.ja.md)は異なるソース開発中の範囲で、参照許可を暗黙に更新しません。通常の本体起動で機能を利用できますが、有効な確認済み許可がなければ、許可を作成したり参照用の接続口を開始したりしません。この手順は公開済み alpha.5 より後のソース開発版を対象とします。

## 対象端末で確認して許可する

1. 保存状態を所有するローカルの本体を起動します。両端末には、同じ有効な管理対象 DirectLAN 接続関係が必要です。
2. `soba resource list` で対象のリソース ID を確認します。
3. `soba resource grant preview --id RESOURCE_ID --peer PEER_KEY --expires-at RFC3339_EXPIRY` を実行します。有効期限には、タイムゾーンを含む有限の将来日時を指定します。
4. 対象と相手の鍵、接続関係、転送の両項目、参照のみの操作、元の有効期限、`initializesState` を確認します。JSON 全体を変更せず非公開ファイルに保存してください。CLI は通常ファイル・サイズ・曖昧でない JSON を検査しますが、ファイルのアクセス権は検査しません。
5. `soba resource grant confirm --review-file REVIEW.json --confirm` を実行します。

preview は保存状態を変更しません。ただし、期限切れや時計の不確実性を観測した場合、安全でないメモリ上の許可を閉じることがあります。古くなった確認内容は拒否し、勝手に新しい内容へ置き換えません。別の有効な許可を作る前に、既存の許可を明示的に失効させてください。

`initializesState: true` の確認には、非公開の許可保存領域の作成も含みます。保存状態全体がないことから、過去の許可がなかったとは判断できません。復旧目的で保存状態を削除しないでください。

## 許可された相手から参照する

対象端末の `soba resource grant inspect --id RESOURCE_ID` が返した正確なリソース ID・許可 ID・変更番号を使います。

`soba resource remote inspect --peer TARGET_PEER_KEY --id RESOURCE_ID --grant-id GRANT_ID --grant-revision REVISION`

出力するのは `transferConcurrentFiles` と `transferConcurrentPerPeer` の指定値と実効値だけです。JSON の名前と値は言語によって変わりません。通信方式やバックエンドを自動で切り替えません。取得できなかった場合、要求したリソースや許可の存在の有無は示しません。

1回の参照には、開始時から合計15秒の期限があります。1回だけのアプリ接続には、認証済み接続の復旧と最大1回の回数・間隔を制限した再接続要求を含め、固定の10秒を使います。参照要求自体を再試行したり、許可の期限を延ばしたりしません。

リソースや許可の指定を含まない固定の hello により、認証済みの管理対象接続で通信方式の互換性を確認します。特定のサービスのプロセス自体を証明するものではありません。対応する hello を確認してから、リソースと許可の指定を送ります。

## 有効期限と準備状態

- 保存した許可は、対象の識別情報・リソース・相手・不変のペア接続関係を保ち、元の絶対的な有効期限まで再起動後も維持します。再起動や再接続で期限を延長しません。
- 非公開の保存状態の所有と永続化、現在の接続関係を再検証してから有効にします。起動ごとに単調時計の上限を保持し、再試行で延長しません。
- `activation` と `listenerReady` により、保存済み許可と、所有する接続口の準備状態を区別します。接続口の準備完了は遠隔参照の成功を保証しません。
- 参照用のユーザー空間ポートは 54546 です。参照機能が未稼働の場合は通常のサービスに使えます。既存の所有者を維持し、競合時には既存サービスを置き換えず、保存済み・未稼働として報告します。
- 失効・期限切れ・保存状態の不確実性・検出した時計の巻き戻りにより、新たな開示を拒否します。失効より前に送信が許可されたサイズ制限内の応答1件は、その後に完了する場合があります。送信済みの内容は取り消せません。

停止中の期限管理は、対象端末の信頼できるシステム時刻に依存します。永続化した観測により一部の巻き戻りを検出できますが、停止中の経過時間を証明したり、非公開の保存状態全体の巻き戻りを検出したりはできません。拒否に至る観測の永続化前に異常終了した場合、その観測を失うことがあります。信頼できる時刻基盤を保証する仕組みではありません。

## 許可の範囲

参照許可は独立して確認します。メッセージ・ファイルへの通常の許可では作成・復元しません。相手への許可全体を取り消す `soba revoke PEER_ID` または Web の「許可を取り消す」は、通常の許可が既にない場合も、対応する参照許可を失効させます。メッセージ・ファイルの停止やサービス共有の停止では、この別の許可を失効させません。管理対象のペアを削除すると、保持した許可が active と表示されていても参照を拒否します。再ペアリングによって古い許可を新しい接続関係へ移しません。

## 失効と確認

現在のローカルの参照結果を使い、`soba resource grant revoke --id RESOURCE_ID --grant-id GRANT_ID --grant-revision REVISION --confirm` を実行します。相手が未接続の場合や期限切れでも失効できます。時刻が不確実な場合も、保存状態の所有を検証できる限り失効できます。

永続化の失敗を成功として扱わないでください。特に、失効の保存が失敗すると、異常終了後の失効は保証できません。不正な保存状態や差し替えを検出した場合は、許可を初期化したり自動修復したりせず、参照機能を停止します。

隔離した架空の2端末相当の Core で、初回の参照、接続を開始する側・応答する側の両方の再起動と元の期限切れ、失効の永続化、既存ポート所有者の維持を検証しています。同じ OS プロセス内で Core.Close/Open を行うテストで、通常の保守処理が先に通信セッションを確立している場合があります。実機、ファイアウォール越え、サスペンドと復帰、OS プロセス自体の再起動、OS ログイン時の受け入れ完了を意味しません。
