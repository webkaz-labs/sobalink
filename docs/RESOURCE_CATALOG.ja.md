# ローカルリソースカタログ

[English](RESOURCE_CATALOG.en.md) · [開発原則](DEVELOPMENT_PRINCIPLES.ja.md)

`soba resource catalog` は、既存の観測を上限内でローカルにまとめて表示します。相手向けのカタログ通信方式・遠隔のリソース列挙・新しい許可・変更操作は追加しません。ソースの動作を説明する文書です。テスト・実機・インストール済みバイナリ・配布には別々の受入確認が必要です。

## まず通常のコマンド

選択したローカル本体を起動して `soba resource catalog` を実行します。最初に `resource.list` で設定の対象を特定し、ローカル設定・保存済みサービス・現在のプロセスの転送状況を1つのカタログ要求で取得します。設定の特定に失敗した場合は、その分類が未解決であることを返します。情報源を黙って減らして完全と表示しません。`resource list` を確認するか、狭い範囲を `soba resource catalog --services --transfers` で明示してください。

操作を通じて共通の `--state-dir DIR` を `resource` より前に指定します。次の操作の案内も同じディレクトリを維持します。`--locale auto|en|ja` は人向け表示の言語を選びます。`--json` は言語によらず同じ検査済みの形式を返します。

## 正確な情報源を選ぶ

情報源フラグを1つでも指定すると、既定の情報源一覧を置き換えます。確認したい情報源のフラグだけを組み合わせてください。

- `--settings`: `resource.list` でローカル設定を1件特定します。
- `--settings-id RESOURCE_ID`: 一覧による特定を行わず、正確なローカル設定の対象を指定します。
- `--services`: 保存済みローカルサービスの観測を選びます。
- `--transfers`: 現在のプロセスの転送状況を選びます。
- `--discovery-peer PEER_ID`: 正確な相手1台の既存サービス発見の観測を選びます。
- `--remote-version 1|2 --peer PEER_KEY --id RESOURCE_ID --grant-id GRANT_ID --grant-revision N`: 既存の許可付き通信方式で、正確な遠隔設定を1件参照します。v1 は対応する参照専用許可、v2 は管理許可を参照にのみ使います。

相手の識別子は最大1つです。サービス発見と遠隔設定を併用するときは、表示名や接続方式の別名ではなく、同じ正確な相手識別子が必要です。全相手への展開・通信方式の自動切替・任意のコマンド名・JSON パッチはありません。接続口を作ったり、信頼関係を変えたりしません。

## 観測を正しく読む

人向け表示には、正確な選択範囲・情報源の状態・観測時刻・行の識別子の有効期間・完全性・一部取得・次の既存操作を含めます。`current` は、その情報源の表示時刻で観測できたことを意味します。常時監視・現在の到達性・全情報源の同時読み取りを意味しません。ローカル設定・保存済みサービス・転送に、架空の到達性の有効期限を付けません。

正常に空と観測した情報源は、取得不能・未確認・上限到達と区別します。一部の行がないことは削除の報告ではありません。失敗した情報源も、成功した別の情報源と独立して表示します。認証済みの相手が明示的に通信方式非対応と返した場合だけ非対応と扱います。一般的なローカル操作の失敗や相手への接続不能だけでは、対応状況は分かりません。

保存型のリソース・サービスの識別子は、その保存記録に伴います。公開されたサービスの ID は今回の有効化中のみ有効です。転送は元のバッチ ID・送信または受信の方向・現在のプロセス内の範囲を維持します。転送行は活動状況であり、ファイルの内容やパスを公開せず、永続的なファイル共有も意味しません。

### サービス発見の制約

今回のソースでは、キャッシュされた `remote_service` の観測を、最近取得した場合や空であることを確認済みの場合も含め、古い・操作に利用できない状態として返します。既存キャッシュには、カタログで現在の観測だと判断するための元の公開元の証拠が十分に保持されていません。不明または混合した接続方式では、取得不能となる場合もあります。`discover --peer PEER_ID` を明示的に実行すると既存のサービス発見は更新されますが、それだけでカタログの制約は解除されません。現在の公開接続へ進む案内を有効にするには、公開元と現在の接続を確認する仕組みの別途レビューが必要です。

## 既存の操作へ進む

カタログは次の手順を案内するだけです。設定の適用・サービスの開始停止・接続・転送の受領や再試行・ファイル選択の起動・共有許可の変更は行いません。

- 設定: 表示された `resource inspect` または正確な `resource remote [manage] inspect` を使い、変更前に既存の情報源で新たな確認を取得します。
- 保存済みサービス: `service show SERVICE_ID` の後、既存の `services start`・`services stop` の手順を確認します。開始停止の事前確認例は共通の `--dry-run` を付けます。サービスが失敗状態なら、既存の操作で実際の有効状態が分かるまで参照のみを案内します。
- サービス発見: `discover --peer PEER_ID` を明示的に実行した後、既存の接続操作でローカルポートと有効期間を確認します。上記のカタログの制約は引き続き適用されます。
- 転送: 既存のローカル UI を開き、同じ相手・方向・元のバッチ ID を探します。再起動後や見つからない転送は同じプロセス内の項目ではありません。自動で操作を開始しません。

観測時刻が新しくても、情報源での新たな許可検査や確認を省略できません。スナップショット ID・epoch・範囲 ID・ダイジェスト・有限の上限は、対応付けや表示のためのデータであり許可ではありません。

## ローカル Web からの画面移動

認証済みのローカル Web カタログでは、設定・保存済みサービス・現在のプロセス内の転送状況について、参照元の選択と更新を明示的に行えます。画面を開いたり本体状態が更新されたりするだけではカタログを取得しません。未解決の種類を残し、不完全な観測を正常な空の結果として扱いません。

設定からは既存の設定確認画面へ、保存済みサービスからは選択した定義の通常の操作へ進みます。転送からは元の現在プロセス内のバッチと方向を選んで表示し、受信承認・再試行・送信は行いません。サービス接続を開く操作は、明示的に選んだ相手の空の手動入力画面を開くだけです。古い広告 ID・ポート・変更番号・有効期間を引き継がず、自動接続しません。新しい選択・確認・許可は既存の接続操作が担当します。キャッシュ済みの探索行は引き続き古い観測として扱い、接続操作を持ちません。

このソース段階では、画面を組み立てた模擬 Web テストと、3つの Core を使う限定ネイティブ試験のローカルカタログ確認が通っています。このネイティブ試験は、空でない実転送状況・実ブラウザー接続・遠隔カタログ機能の許可を実証するものではありません。

## Dry run と安定した JSON

共通の `--dry-run` は本体への接続を一度も行わず、プロファイルを書きません。ローカル設定の ID が不明なら、`unresolvedSources` に `local_settings` を含め、`requiresResourceList: true` を返します。具体的に選択済みの情報源はデータとして `resolvedSources` に残ります。架空の対象や実行可能なカタログ要求は作りません。ID の特定を行わず具体的な設定の選択を検査したい場合は、`--settings-id` を指定してください。

`--json` は、閉じた応答形式・有限の上限・要求した情報源との正確な一致・カタログ全体のダイジェストを検査してから表示します。外側の項目は `schemaVersion`・小文字開始の camelCase の `limits`・`snapshot` です。項目名やユーザーの値を翻訳しません。人向け表示に生の情報源エラー・情報源の非公開パス・表示名から組み立てた任意のシェルコマンドを含めません。

独立した遠隔カタログの権限・形式、より高度な永続的ファイル共有、ブラウザー・ネイティブ統合、全体の回帰検査、署名付き配布は、それぞれ別の確認事項です。
