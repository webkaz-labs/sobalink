# 開発・使いやすさの基本方針

[English](DEVELOPMENT_PRINCIPLES.en.md) · [利用ガイド](GENERIC.ja.md) · [設計と検証](ARCHITECTURE.md)

**少ない操作で目的に進め、必要なときだけ詳しくできること。** この方針は、実装・レビュー・文書更新で共通して使います。CLI とローカル画面の双方に同じ基準を適用します。

## 1. 日本語と英語をどちらも正式に扱う

- 基本は OS／実行環境のロケール自動判定。日本語なら日本語、それ以外は英語へ安全にフォールバックし、明示的な切替も用意する
- ヘルプだけでなく、初回案内、質問、確認、状態、エラー、次にすることまで対応する
- コマンド名・オプション名・機械向け JSON の契約は言語で変えない。接続先・識別子・利用者が入力した値を翻訳しない
- ブラウザーを開けない、QR が読めない、端末幅が足りない場合にも、その場で使える代替手段を示す

## 2. 簡単さと柔軟さを両立する

- よく使う用途には妥当な候補を用意する。候補を決定済みの事実として扱わず、実際のサービスに合わせて変更できるようにする
- 必須入力は目的に必要な分だけ。通常の設定で JSON 編集や内部の識別子入力を要求しない
- 通常操作、詳細設定、診断の順に見せる。最初のヘルプに全機能を並べすぎない
- 同じ操作の繰り返しで、意図せず再作成・再承認・範囲変更しない。異なる対象・期限など重要な変更は明確にする
- 入力間違いは可能ならその項目で直せるようにし、確認前には編集・戻る・取消の道を用意する

## 3. 状態と次の行動を明確にする

- 相手、対象サービス、実際の接続先、期限、開始／停止状態が分かるようにする
- エラーには原因として分かっていることと、具体的な次の一手を添える。分からない原因を断定しない
- 設定保存、待受準備、アプリの成功、遠隔ジョブ完了を混同しない。一部成功を全体成功にしない
- 別プロフィールを選んだときは、案内する次のコマンドも同じプロフィールを保持する
- 画面がある場合は、情報の優先順、操作の位置、戻る導線、狭い画面、コントラスト、文字サイズまで確認する

## 4. 文書は結論と短い手順から

- 冒頭で「何ができるか」「どの版で使えるか」「未確認の範囲」を区別する
- まず最短の通常手順を示す。詳しい条件や例外は後ろ、必要なら折り畳みへ置く
- 用語を統一し、比較は表、流れや関係は Mermaid などの図を使う。図・リンク・コード例も実際に検査する
- 実装済み、模擬試験済み、配布確認済み、実機確認済みを分け、証拠の範囲を超えて保証しない
- 同じ方針を複数ファイルへ重複して固定せず、この文書を参照する

## 変更時の確認表

- [ ] 日英の初回案内、ヘルプ、確認、状態、エラーと次の操作を確認した
- [ ] ロケール自動判定・明示切替・未知ロケールのフォールバックを試した
- [ ] 初回設定 → 認証 → 接続 → 利用先表示 → 停止の流れを通した
- [ ] 取消、編集／戻る、再試行、繰り返し操作、途中失敗、空の状態を試した
- [ ] 競合や権限不足で、無言の設定変更をせず代替手段を案内することを確認した
- [ ] QR・文字・表の幅とコントラスト、出力の情報量を確認した
- [ ] JSON と利用者の値が翻訳や表示処理で変わらないことを確認した
- [ ] 対象 OS の自動試験・配布確認と、未実施の実機試験を区別して記録した
- [ ] 文書のコマンド・対象版・リンク・図と実装が一致している
