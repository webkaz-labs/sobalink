# tsnet-bridge 次期機能計画

更新日: 2026-10-01

次の開発では、**名前付きの複数転送と、tailnet から明示したローカルサービスへの逆向き接続**を中心に、設定・診断・停止までの操作を整えます。これにより、Web/API/DB のまとまった利用、ローカル AI・テスト API の限定共有、複数端末の AI エージェント連携を検討できます。用途は [活用案](USE_CASES.ja.md) にまとめています。

**本書は `0.1.0-alpha.2` の後に取り組む計画です。以下の機能は未実装・未検証で、同プレリリースには含まれません。** 実装を開始した、接続先を追加した、アクセスを許可したという意味ではありません。日程や次の版番号は未定です。既存版の導入・試験は [日本語手順](VERIFICATION.md)、実装と自動試験の根拠は [検証報告](VERIFICATION.en.md) を参照してください。

## 現状から変更する点

現在の [設定](https://github.com/webkaz-labs/tsnet-bridge/blob/0069e38732227c8913ee6ceb0ec21784ae03d862/internal/config/config.go) は RustDesk の公開鍵と ID・ID−1・relay のポート構成が必須です。転送先にも 1024 以上の制約があり、標準の SSH `22` や HTTPS `443` は指定できません。基盤には固定 TCP／UDP 転送と認証付き SOCKS CONNECT がありますが、任意の名前付き転送や tailnet 側の受信待受はありません。

次期設定では、RustDesk 固有の条件を専用プロフィールに残し、汎用の転送ルールと分けます。設定の移行は内容を事前表示し、既存プロフィールを無断で変換・有効化しません。

通常の Tailscale には直接接続と ACL/grants、Serve によるローカルサービスの提供・複数 TCP 設定・JSON 状態表示が既にあります。本計画の狙いは、独立した tsnet ノードで、用途別プロフィールとタスク単位の接続管理を揃えることです。既存構成で足りる用途ではそれを優先し、接続制限や逆向き提供を bridge 固有の安全性・機能とは説明しません。比較と運用負担は [活用案の使い分け](USE_CASES.ja.md#通常の-tailscale-との使い分け) を参照してください。[Serve の公式仕様](https://tailscale.com/docs/reference/tailscale-cli/serve)

## 二つの接続方向

| 方向 | 計画する経路 | 接続開始を受ける場所 |
| --- | --- | --- |
| 外向き転送 | ローカルアプリ → loopback 待受 → 指定した tailnet ピアのサービス | ローカル端末だけ |
| 逆向き転送 | 許可した tailnet ピア → bridge の tsnet 待受 → 明示した loopback サービス | bridge の tailnet ノード |

逆向きとは、相手から新しく接続を開始できることです。既存の TCP 接続内の応答や UDP の返信とは区別します。

TCP 逆向き転送は `tsnet.Server.Listen` を入口とし、転送先を明示した数値の loopback アドレスとポートに限定する設計です。既存サービスの待受を全インターフェースへ変更する必要を減らしますが、今までローカルだけだったサービスへ遠隔から届くようになるため、アクセス範囲は広がります。保存だけでは待受を開始せず、対象・許可する相手・期限を確認してから有効にします。[固定依存版の tsnet Listen](https://pkg.go.dev/tailscale.com@v1.102.5/tsnet#Server.Listen)

外向きの接続先を OS の通常経路へ切り替えるフォールバックは引き続き禁止します。逆向きで使うローカル接続は、明示された loopback 転送先専用の別経路として実装し、LAN・公開 IP・任意のホスト名へ流用できないようにします。OS の経路・DNS・ファイアウォール設定を自動変更する計画ではありません。

## 機能と操作

### 名前付きの複数転送とグループ

- 各ルールに名前、方向、TCP/UDP、待受ポート、転送先、個別の有効・無効を持たせる
- `web`、`api`、`database` などを一つのプロフィールにまとめ、全体または必要な項目だけを開始・停止できるようにする
- 逆向きルールには許可する接続元ピアと期限を追加する。同じ tailnet にいる全員を自動で許可しない
- グループの存在と、全項目の有効化を分ける。新規・取り込んだルールは無効から始め、秘密情報を共有用設定へ含めない
- 同じローカル接続先を使って環境を切り替える場合は、現在のプロフィールと実際の接続先を明示する。確認前に切り替えず、既存接続を別環境へ付け替えない
- グループ開始前に選択項目の競合を確認する。開始途中で失敗した場合は、その操作で新しく開いた待受を戻し、既に使われている無関係な転送を止めない
- 一部だけ接続不能になった場合は項目別に状態を表示する。認証やピア情報など共通の安全条件が失われた場合は、影響する転送を閉じる

### 接続先選択とポートの提案

現在の tailnet ピアから接続先を選び、名前と識別情報を確認できるようにします。端末が一覧にあることを、サービス稼働やアクセス許可の証明にはしません。同名の端末への置換で接続先が自動的に切り替わらないよう、保存先の識別方法も設計します。

汎用プロフィールでは、同じポート番号を最初の候補にします。競合やローカル待受の権限制約がある場合は代替候補と影響を表示し、確認後に変更します。管理者権限の取得や無言の自動変更で解決しません。TCP と UDP が同じ番号を必要とする組み合わせはまとめて確認します。

RustDesk の relay など相手へ伝播するアドレスは、既存の固定ポート条件を維持します。一般用途の代替ポート機能を、そのまま適用しません。

表示では、アプリに入力するローカル待受、SOCKS のプロキシ欄と最終宛先、逆向き提供の tailnet 側入口を区別します。同じポート番号でも IP は同じにならず、bridge が相手の tailnet IP への OS 経路や MagicDNS を追加するわけではありません。入力先の対応は [活用案のアドレス説明](USE_CASES.ja.md#アプリに指定するアドレス) を参照してください。

### 接続情報のコピーとアプリ起動

URL、SSH/SFTP の接続情報、実際に選ばれたポートをコピーし、対応アプリを起動できるようにします。HTTPS の証明書名・SNI・Web の origin、SSH のホスト鍵を維持できる経路を確認してから案内します。

HTTPS の宛先を localhost に書き換えるだけでは証明書名が合うとは限りません。証明書確認の無効化を自動生成しません。SSH の `HostKeyAlias`、CLI での curl `--connect-to` などは用途に応じた候補であり、全アプリに共通の解決策ではありません。既存アプリの設定ファイルの自動書き換えは別途の明示操作にします。[OpenSSH](https://man.openbsd.org/ssh_config#HostKeyAlias)、[curl](https://curl.se/docs/manpage.html#--connect-to)

### 逆向きの共有状態と停止

有効な逆向きルールを常に一覧で確認できるようにします。表示項目は、サービス名、tailnet 側の入口、ローカル転送先、bridge 内で許可した接続元、残り時間、状態です。tailnet 側の実効ポリシーを確認できない場合は、確認できた範囲を明示します。

- 個別停止と逆向き転送の全停止を用意する
- 初期は期限付きの有効化を基本とし、期限到達時は新規待受だけでなく既存の転送と UDP 対応表も閉じる
- 停止・期限切れのルールを、再接続や再起動だけで有効に戻さない
- スリープ中に期限を過ぎた場合は、復帰後に通信を再開する前に閉じる。時計変更と再起動を含む期限の扱いも試験する
- 期限は接続を閉じるためのもので、既に相手へ渡ったデータを削除・回収するものではないと表示する

### 再接続と診断

スリープ復帰、ネットワーク変更、一時切断後に、同じ認証状態と確認済みの接続先で復旧できるようにします。確認できない状態では通信を閉じる fail-closed を維持し、通常経路への切り替え、別ピアへの付け替え、期限の延長を行いません。

診断は「未認証」「ノード承認待ち」「ピアを確認できない」「ローカルポート競合」「転送先へ接続できない」「期限切れ」など、観測できた段階で区別します。TCP タイムアウトだけで ACL 拒否・相手停止・経路障害のどれかに断定せず、確認できない原因は候補として表示します。TCP 到達、UDP の応答確認、アプリの成功は別の結果にします。

### 希望した場合だけの自動起動

手動開始・停止と復旧の動作を検証した後で、ユーザー単位の自動起動を検討します。既定は無効で、登録・解除方法を表示します。自動起動の許可を、全ルールの有効化や逆向き共有の再開許可と混同しません。逆向きの継続共有には対象・相手・継続条件の別指定が必要で、期限切れを復活させません。

## AI エージェントと自動処理への接続インターフェース

bridge は、オーケストレーターが指定した接続を準備し、状態を返し、後片付けする役割を担います。ジョブの割当、実行権限、結果回収、実行の再試行・重複防止は、外部のオーケストレーターと各端末のサービス API の役割です。bridge に特権付きの任意コマンド実行 API を追加する計画ではありません。

現在も `status --json` はあります。次期では、それを次の単位へ広げる案です。以下の操作名は機能の呼び方で、利用可能な新 CLI の構文ではありません。

- **ルール単位の JSON 状態・診断:** プロフィール、ルール、方向、観測した状態、理由コード、確認時刻、実際の待受、期限を機械可読で返す。認証情報は含めず、未知の原因とアプリの検証状態を区別する
- **期限付きの準備待機:** 指定したルールの準備を待つ `wait-ready` 相当の操作。タイムアウト・取消・一部失敗を返し、準備できたことと遠隔ジョブの完了を混同しない
- **タスク単位の開始・停止:** 実行ごとのプロフィールまたは所有関係を管理し、自分が開始した転送だけを停止する。共有中の転送を別のタスクが片付けない。単なる名前分けは OS のセキュリティ隔離ではない
- **取消と後片付け:** 通常終了・例外・呼出元の終了・期限切れで接続を片付ける。途中失敗後の再確認や同じ停止要求の繰り返しで、他のタスクの資源を変更しない

**回線の切断や TTL は、遠隔ジョブの取消・処理の巻き戻しを保証しません。** 実行側にはジョブ ID、重複を避ける受付、取消と結果照会の API が必要です。オーケストレーターが安全な再試行と最終結果を確認し、bridge はアプリ要求を勝手に再送しません。

HTTP 型 MCP やローカルツール API は、別途認証を備えたサービスへの TCP 接続として扱う候補です。MCP の Streamable HTTP と stdio は異なるトランスポートで、stdio のサブプロセスを TCP 転送だけでリモート MCP サーバーに変換することはできません。対応する HTTP サーバーまたは別アダプターが必要です。[MCP トランスポート仕様](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)

tailnet への接続許可は、ツールでファイルを読む・変更する・コマンドを実行する許可とは別です。HTTP MCP/API 側で認証、操作・引数・対象資源の認可、必要な利用者確認を行います。サービスの URL を変える場合は TLS、認証の宛先、origin も検証します。bridge から権限・トークン・CLI の承認を無断で追加しません。[MCP 認可仕様](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)、[ツールの利用者確認](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

各エージェントの実行環境には、対象 tailnet へ到達するための明示的に承認された接続と、サービスの利用権限が必要です。SaaS 上のエージェントが URL を知るだけで接続できるわけではありません。また、この接続経路を絞っても、エージェントの他の OS 通信経路やファイル権限は制限されません。実行のサンドボックスや秘密情報の隔離は、別の実行環境設計です。

## モバイルからの利用と追加の検証対象

通常の Tailscale に接続済みの iPhone/iPad から、PC 側の次期逆向き転送へ Safari や既存アプリで接続する構成を検証候補にします。この用途のための iOS 版 bridge は計画しません。入口は提供側 bridge の tailnet 名とポートで、iOS 側の localhost ではありません。

Web の実機確認、AI Web UI、ダッシュボード、既存ファイルサービス、対応クライアントでの SSH が候補です。MagicDNS、サービスのログイン、TLS・secure context、画面ロック・バックグラウンド・回線切替後の再接続を実機で確認します。tailnet 内の HTTP でも、カメラ・マイク等に必要な secure context が自動で成立するわけではありません。証明書発行・OS の経路や DNS の変更を勝手に行わず、必要なら別の明示操作にします。[Tailscale iOS](https://tailscale.com/docs/install/ios)、[secure context の条件](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)

tailnet 内のコールバック受信、読み取り専用の障害診断、限定した遠隔デバッグ、MQTT 接続も、同じ基盤を使う候補です。公開 SaaS の webhook 受信や、非 tailnet の IoT 機器への任意 LAN 中継は含めません。デバッグのような高権限の入口は、認証・接続元・期限を特に厳しく制限し、自動で再共有しません。

## 逆向き接続で追加する安全条件

1. **接続元と転送先を両方制限する。** tailnet のアクセス制御に加え、ルール単位の接続元ピア許可を検証する。ピアの識別・現在性を確認できなければ拒否する。全ポートや全 loopback サービスの自動公開はしない。[Tailscale のアクセス制御](https://tailscale.com/docs/features/access-control/grants)
2. **ローカル扱いによる認証回避を確認する。** 逆向き先のアプリからは bridge の loopback 接続に見える。「localhost なら認証不要」という設定も遠隔に届くため、必要なアプリ認証や認証付きゲートウェイを用意する。受信側の元の端末 IP が透過的に残るとは仮定しない。
3. **許可の失効を考慮する。** 接続開始時と稼働中に確認できる認証・ピア状態を再検証し、失効・識別変更を観測したら対象の既存転送も閉じる。制御情報の伝播前まで含む瞬時の失効は保証しない。
4. **上限を持つ。** 接続数、UDP 対応表、待ち行列、アイドル時間を制限し、相手別の取り違えや資源枯渇を防ぐ。
5. **共有の範囲を見せる。** 保存と有効化を分離し、開始前に対象・相手・期限を表示する。診断や設定の書き出しには秘密情報を含めず、共有前に確認できるようにする。

ローカル待受は引き続き他のローカルプロセスから到達でき、アプリ単位の完全な隔離は提供しません。詳しい既存の境界は [セキュリティ](../SECURITY.md) を参照してください。

## UDP は TCP と分けて設計する

外向きの固定 UDP 転送には既存基盤がありますが、逆向き UDP は別の設計・試験対象です。依存している tsnet の `ListenPacket` は IP アドレスの明示を要求するため、TCP の待受実装をそのまま流用できるとは扱いません。[固定依存版の ListenPacket](https://pkg.go.dev/tailscale.com@v1.102.5/tsnet#Server.ListenPacket)

逆向き UDP では、接続元のピアと送信元ポートごとにローカル側の対応を維持し、遅延応答を正しい相手に返す設計が必要です。失効・期限・アイドル終了後の応答を別の相手へ送らず、受信・送信の双方で許可を検証します。TCP と同じ「接続できた」という診断を流用せず、UDP 専用の模擬試験と実アプリ試験を通してから提供を判断します。

## 実施順と完了条件

| 段階 | 実装・検討対象 | 次へ進む条件 |
| --- | --- | --- |
| 1 | 設定スキーマ、名前付き複数ルール、既存設定との分離 | 移行・検証・個別無効化で既存動作と許可範囲が変わらない |
| 2 | 外向き複数 TCP／UDP、グループ、ピア選択、ポート提案、項目別 JSON | 競合・部分失敗・個別停止・許可違反の自動試験が成功 |
| 3 | 逆向き TCP、接続元制限、状態一覧、停止、期限 | 拒否・失効・期限・既存接続の終了を含む自動試験と実機確認が成功 |
| 4 | 逆向き UDP | 対応表の分離、非同期応答、失効・期限・上限・実機動作の確認が成功 |
| 5 | 復帰・再接続、診断、URL/SSH コピー・起動、タスク単位の準備待機・終了 | OS 別の障害復旧、並行タスクの所有関係、名前・認証の検証が成功 |
| 6 | ユーザー単位の希望制自動起動 | 登録・解除・二重起動・停止保持・期限切れ非復活の確認が成功 |

安全条件と基本診断は各段階の実装に含めます。段階 5 まで後回しにはしません。TCP 逆向きの成立を UDP 逆向きの合格根拠にせず、既存版の実機確認で見つかった問題も各段階へ反映します。

### 試験で最低限確認すること

- 設定保存・再読込・移行、重複名、ポート範囲、方向・プロトコルの不整合、無効な項目が起動しないこと
- 同じピアの複数サービス、複数ピア、TCP/UDP の同一番号、ポート競合、グループ開始の巻き戻し、個別停止の独立性
- 許可していない接続元、識別不能、同名ピアの差し替え、失効、tailnet ポリシー拒否、通常経路へのフォールバックがないこと
- 逆向きから指定外の loopback ポート・LAN・公開アドレスへ到達できないこと、ローカルサービスの認証が維持されること
- TCP の半閉じ・切断、UDP の複数送信元・順不同・遅延応答・アイドル・対応表上限、停止後の残存通信
- 期限到達・スリープ中の期限切れ・再起動・時計変更・ネットワーク切替・長時間切断後に意図しない共有が再開しないこと
- HTTPS の証明書名・SNI・origin・リダイレクト・WebSocket、SSH のホスト鍵確認、実際のアプリ操作
- 通常の Tailscale を使う iPhone/iPad からの名前解決・認証・画面表示・入力、画面ロックと復帰。ブラウザー機能の権限と secure context は個別に確認する
- 固定ローカル接続先での環境切替時の誤接続防止、プロフィール・接続先表示、既存接続の扱い
- JSON の互換性と秘密情報の非出力、準備待機のタイムアウト・取消、並行タスクの独立性、二重停止、呼出元終了時の後片付け
- HTTP MCP/API の認証拒否・権限不足・応答ストリーム中断、切断後も続くジョブの状態照会、接続復旧でアプリ要求を自動再送しないこと
- Linux・macOS・Windows の対象構成。Windows の管理者権限 CI と、標準ユーザーでの起動・認証を別に記録する

自動試験は実際の tailnet 認証を行わない構成を基本とします。実機の参加・共有・ポリシー変更は対象と範囲を承認した試験で別に確認します。CI の成功だけで実機互換性を合格扱いにしません。

実用性の判断では、通常の Tailscale／Serve と設定・終了操作の手間を比較し、追加ノード・保存状態の運用負担も確認します。常駐時の CPU・メモリー・電池、複数転送の速度、direct／DERP の条件を測定し、未測定の軽量性・高速性を利点として扱いません。

## 今回の計画に含めないもの

独自ファイル同期、クリップボード同期、チャット、バックアップ実行エンジン、エージェントのスケジューラー・任意コマンド実行・stdio MCP アダプター、ブラウザー向け HTTP プロキシ、無人環境の認証方式追加は別機能です。今回増やすのは接続の基盤と操作であり、これらのアプリ機能を自動的に提供するものではありません。

公開インターネットへの提供、Funnel、サブネット転送、Exit Node、mDNS・ブロードキャスト中継、任意宛先への転送も対象外です。新しいアクセス許可・OS 設定・既存アプリ設定を自動で広げず、必要な変更は目的と影響を明示した別操作にします。
