# ローカルリレーの設定と復旧

[English](RELAY_OPERATIONS.en.md) · [利用ガイド](GENERIC.ja.md)

このデバイスのプライベートアドレスを明示的に選び、リレーを起動して相手を非公開でペアリングします。設定の保存、待ち受けの準備完了、相手やアプリとの通信成功は別の状態です。ネイティブのループバック試験だけでは、実際のLAN到達性、スリープ復帰、アプリ互換性は確認できません。

## LAN内とLAN外の使い分け

LAN外はTailscaleを推奨します。この設定で起動する中継は、明示したprivate／loopbackアドレスと非特権TCPポートだけを対象にします。専用の公開中継デーモンや外部への配備手順は提供していません。既存の高度なtrusted-relay設定は到達可能な互換中継の数値端点と証明書pinを指定できますが、中継サーバーやbootstrap認可を用意する機能ではありません。LAN中継は既存のネットワークで両方の相手から到達できる必要があります。ルーター・FW・管理者権限の変更を要求・実行しません。

接続成立後のアプリ通信は中継を通らず直接通信できる場合がありますが、Tailcatは初期ペア設定・presence・端点変更の通知にも中継を使います。成立済みloopback経路で中継停止後に通信できたことは、中継なしの初回起動やネットワーク変更後の復旧を証明しません。中継なしLANは別途ペア設定したdirect-LAN方式を使い、固定した制御TCPとWireGuard UDPの両方に到達できる必要があります。

## 通常の設定

1. `soba start --offline` で起動し、`soba lan addresses` で候補を確認します。ローカルWeb UIでは「このデバイスでリレーを起動」を選びます。候補にVPNのアドレスが含まれる場合もあるため、インターフェースを確認してください。
2. アドレスと未使用の高位TCPポートを選び、`soba setup --network lan --host ADDRESS:PORT` を実行するか、Web UIで内容を確認して起動します。UIが先頭の候補を自動選択することはありません。
3. `soba status` またはリレー概要で、保存状態と待ち受け状態を確認します。待ち受けの成功は、他の端末から到達できる証拠にはなりません。待受に失敗しても保存済みIDは残ります。報告された原因を確認してから再試行し、別の端点に変更する場合は明示的に確認してください。他のアプリの停止やファイアウォール変更は自動で行いません。
4. `soba lan --help` に従って、相手を指定した招待を非公開で確認・交換します。ペアリングとアプリの信頼は別々に許可します。
5. `soba stop` またはUIの「sobalink を停止」で、アプリ全体、リレー、現在のサービス接続を停止します。同じ設定で再起動するとIDを維持しますが、アプリ側では再接続が必要な場合があります。

別のプロファイルを使う場合、各コマンドの前に同じ `--state-dir PATH` を指定してください。そのプロファイルだけを操作します。リモートインストール、自動起動登録、ファイアウォール変更、リレーの自動選出は行いません。

## 待受の状態と起動失敗の診断

現在のソースでは、所有するリレーの処理終了を状態に反映します。リレー待受または非公開の入場確認待受が終了すると両方を閉じ、ホストを準備完了と表示しなくなります。リレーの自動再起動や端点変更は行いません。復旧時はsobalinkを停止し、保存済みの設定で開き直してください。停止の対象は引き続きアプリ全体です。

mixedモードでもLANの状態は該当するLANワーカーだけから取得し、他の接続方式の準備完了とは分けます。`readinessKnown: false` は現在の状態を取得できなかったことを表し、CLIとWebは停止と断定せず状態未確認と表示します。この応答の既存の準備完了フラグはfalseのままなので、利用側は先に `readinessKnown` を確認してください。この項目は追加項目であり、項目のない従来の応答の解釈は変わりません。状態取得では到達性のプローブを行いません。

この型付き起動診断の対象は現在、単独のLANモードです。mixedモードのLANワーカーが制御チャネルの開始前に失敗した場合は、引き続き原因未分類の起動失敗になることがあります。

ポートの競合、アドレス・アドレス系統の利用不可、待受権限の拒否、待受資源の不足は、OSが対応する型付きのローカル待受エラーを返した場合だけ分類します。それ以外は原因未分類のままとし、生のエラー詳細は公開しません。ポートの競合は他のプログラムの停止やポート変更の許可ではなく、アドレスの利用不可も証明書変更の許可ではありません。保存済みの鍵、指紋、ペア、ポリシーは保持します。

## 証明書とアドレスの変更

ホスト証明書はIPに対応しています。通常の設定の再実行では、有効な証明書を維持します。ポートだけの変更では証明書と指紋を維持しますが、接続先の変更になるため保存済みペアの解除が必要です。状態表示には有効期限が表示され、30日以内なら注意を示します。期限切れ・有効期間前の場合は、更新前に時計を確認してください。

既存の証明書の更新には、別の明示的な選択が必要です。IP変更や証明書の無効化によって、指紋を自動で作り直すことはありません。

1. 対象端末で保存済みLANペアを明示的に解除します。再度許可するアプリの範囲も確認し、以前の信頼がそのまま適切とは決めつけないでください。
2. ホストを停止し、`soba start --offline` で起動し直します。
3. `soba setup --network lan --host ADDRESS:PORT --rotate-certificate` を実行します。Web UIではホスト設定の確認画面で「保存済みのリレー証明書と指紋を更新する」を選んでから起動します。取消では何も変更しません。保存済みペアや稼働中のエンジンがある場合、更新を拒否します。
4. 新しいアドレスと指紋を非公開で確認します。相手側をその正確な接続先に設定し、新しい招待で再ペアリングして、アプリの信頼も別途許可します。古い指紋での接続は失敗したままで、自動上書きや別リレーへの自動切替はありません。

更新ではデバイスの公開IDを維持し、リレーIDを新しく作成します。保存の失敗時に新しいIDをメモリへ公開しません。永続化が不確実と表示された場合は、停止して保存状態を確認してから再試行してください。失敗を隠すために非公開状態を削除しないでください。

## 検証範囲

架空データの試験で、明示的更新、再実行時の維持、同じIPでのポート変更、IP変更、ペア・エンジンが残る場合の拒否、保存失敗、証明書状態、日英の表示、UI確認・取消を確認します。これは製品の自動試験であり、実機のペアリングやネットワーク隔離の受入完了ではありません。実機試験には明示的に許可した端末・ネットワークだけを使い、実際のアドレス、インターフェース一覧、ID、招待ではなく一般化した結果を公開してください。

## 接続前にLAN接続先の許可範囲を選ぶ

既定の `trusted-relay` では、通常の直接接続先や選択済みリレーの診断通信を許可します。明示的に設定した外部リレー宛ても含みます。最初の接続から下位ネットワークの接続先を制限するには、初回設定で同時に選びます。

```sh
soba setup --network lan --host ADDRESS:PORT --policy-mode allowed-lan-destinations --prefix PRIVATE_CIDR
```

参加側では `--host` の代わりに `--relay ADDRESS:PORT --certificate SHA256` を使います。確認した範囲を追加する場合は `--prefix` を繰り返します。Web UIではホストや招待の確認前に「詳細: 接続先の許可範囲」を選べます。アドレス一覧の範囲は候補であり、自動では許可しません。選択済み・追加候補のリレーは許可範囲に含める必要があります。ポリシーとリレーを一緒に保存してから通信を開始します。

既存の設定は、停止してオフラインで開き直し、`soba lan policy show` で確認してから `soba lan policy set --mode allowed-lan-destinations --prefix PRIVATE_CIDR` で変更します。この保存操作ではネットワークを開始しません。Web UIでも同じオフライン変更を確認して保存します。意図的に範囲を広げるには、範囲を指定せず `--mode trusted-relay` を選びます。確認画面には広がる接続先の説明が表示されます。相手の信頼と経路許可は別の設定です。

範囲は接続先アドレスを表し、物理インターフェースへの固定を意味しません。一致するアドレスもVPN・トンネル・別のネットワークを経由する場合があります。物理LANの隔離や端末全体の外部通信ゼロを証明するモードではありません。ポリシー保存に失敗すると、そのプロセスでは復旧まで変更を停止します。新しいプロセスが読み込む実際のファイルには以前のポリシーが残る場合があります。失敗した要求を、永続的な制限の成立と扱わないでください。

## 候補情報と変更可能なリレー予算

候補の許可数を4件に固定する制約はありません。4件を超える正確な候補も保存・交換し、明示的に許可できます。保存情報は `lanStateBytes`、既存の署名付き交換形式は本文24 KiB・封筒64 KiB、DERPはゼロを除く16ビットの識別子空間に制約されます。これは保存・プロトコルの制約であり、NATの対応能力を表すものではありません。旧版は4件を超える提供情報を拒否するため、多い候補を使う前に両端を更新してください。また、明示的に保存した新しいリレー予算キーを旧版は認識しないため、その状態をダウングレードする前に互換性の確認が必要です。旧状態の読み込みでは、既存ペア、有効期間、指紋、明示的な許可を変更しません。

サーバーは設定した各リレーへの接続を維持します。有効なリレーマップは診断先の範囲も制約します。選択した同時接続予算を超える起動は、通信を始める前に拒否します。保存済み候補と許可は残ります。新しい接続先の許可と混同せず、予算を明示的に増やしてください。

```sh
soba lan resources show
soba lan resources set --presence-connections 8 --candidate-attempts 8
soba lan resources set --tls-connections 128 --admission-connections 32
```

先にネットワークを停止し、`soba start --offline` で開き直します。選択したプロファイルを使う場合、各コマンドの前に同じ `--state-dir PATH` を付けます。`set` は現在の容量設定の版を確認し、未指定の設定を維持します。`--dry-run` は本体に接続せず、指定した変更だけを表示します。個別の値に `default` を指定すると既定値へ戻します。Web UIの「容量と履歴 → その他の上限とリソース予算」でも同じ予算と次回起動時の反映案内を表示します。稼働中のネットワークがある場合は、予算の変更前に停止が必要です。

| リソースキー | 安全な既定値 | 対象 |
| --- | ---: | --- |
| `relayPresenceConnections` | 4 | 同時に維持するサーバー側リレー接続とリレーマップの診断先数。多いマップを有効にするには明示的に増やします |
| `relayCandidateAttempts` | 4 | 管理対象の接続1回で順番に試す許可済み候補数。型で確認した到達性エラー後に位置を進め、後の候補も次の接続で試せます |
| `relayTLSConnections` | 64 | この端末の組み込みリレーが受け入れるTLS接続数 |
| `relayAdmissionConnections` | 16 | 非公開ループバックの入場確認コントローラーが受け入れる接続数 |

予算は正の有限整数です。同時リレー・試行予算は、ゼロを除く16ビットのDERP識別子空間（65535）以内です。接続数は実行環境のカウンターとJSON整数表現に収まる必要があります。枠が満杯なら超過した接続だけを閉じ、接続を閉じると枠を返します。既存のハンドシェイク・ヘッダー待機時間と2分のリレー接続リースは維持します。予算を増やすとソケット・メモリー・CPU使用量が増える場合があります。自動起動、新しいリレー宛ての許可、OS経路、外部探索を有効にする操作ではありません。

復旧の再試行は到達性が確認できるエラーに限り、順番に行い、既存の呼び出し側の期限も維持します。TCPの接続拒否・到達不能・リセットなら別の許可済み候補を試せます。一般的なタイムアウト、原因不明の確認失敗、取消、指紋・認証・権限エラー、またはそれらを含む複合エラーでは停止します。保守対象のエンジンは現在の接続世代のdial・TLS・protocol失敗を型付きで通知します。明確に分類したdialの到達性エラーだけで別候補を試し、TLS・入場認可・protocolの失敗では停止します。古い通知で現在の状態を上書きせず、一度確認した停止対象の失敗は内部再接続でも保持し、実際の中継入場成功で初めて解除します。原因を分類できなければ推測せず停止します。nativeの失敗通知と最終ソースの復旧試験は公開前の必須条件です。
