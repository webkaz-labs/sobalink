# sobalink の確認範囲

[English](VERIFICATION.en.md) · [使い方](GENERIC.ja.md) · [配布](DISTRIBUTION.md)

**新しい sobalink の開発版であり、新しい公開版の検証完了ではありません。** 最初のスナップショットにはローカル画面、共通 CLI、本体、Tailnet、文字・一括転送、サービス範囲を含めます。Tailcat はこの版では利用できず、統合を継続します。旧版の合格結果をこのソースの証拠にはしません。

## 結果を区別する

| 区分 | 現在の意味 |
| --- | --- |
| ソース実装 | 最初の版に Tailnet・Web・CLI・転送・範囲共有のコードがある |
| 単体・模擬・race 試験 | 許可、保存、上限、範囲処理、画面操作を個別に検査。実行した結果だけを記録する |
| ネイティブ全試験 | 現在のクラウド実行環境はソケット作成を `operation not permitted` で拒否。実行不能を成功扱いにしない |
| 実ブラウザー受入 | Go 本体を使う CI の準備済み。対象ソースの結果と画像を得てから合格にする |
| 実ネットワーク・アプリ | 認証、2台での受渡し、ACL、直接・中継の変化、実アプリは未検証 |
| 署名付き sobalink 公開 | リリース番号未定。新しい公開版の存在を主張しない |

実装中に画面コンポーネントの44試験が通りました。テスト環境での結果であり、Go サーバーを使う実ブラウザーの合格ではありません。その後の変更には影響する検査を再実行します。CI は正確なソースコミットに結び付け、新しい変更へ古い結果を流用しません。

## ネイティブと画面の条件

Linux x64/ARM64・macOS ARM64・Windows x64 の race/vet、IPC とソケットの片付け、配布物の実行、日英表示を維持します。クロスコンパイルはネイティブ実行の代わりになりません。ホスト型 Windows CI の成功と、標準ユーザーでの実認証も別です。

画面は実際の Go プロセスと埋込み資材で検査します。コード入力、有効期限・再利用拒否、セッション切れ、移動・戻る・取消、重複操作、古い状態、エラー、キーボードとフォーカス、日英、明暗、狭い表示を確認し、そのビルドの画像を記録します。サーバー起動失敗はブロッカーで、画面の合格ではありません。

誤った Host/Origin、CSRF 不足、別セッション、過大要求、ピア API からの管理操作を拒否する試験も必要です。コード・認証 URL・capability を URL や通常の状態に漏らさないことを確認します。

## 実際の2台で確認する順序

一般的な例を使い、必要な接続・アカウント権限を得ます。ソース、版、OS、ネットワーク、結果、最初の失敗箇所を記録し、非公開状態は公開しません。

1. 新しい状態でネットワーク未選択を確認し、独立 Tailnet ノードを認証して意図した相手を確認する
2. 受信側で正確な送信者を信頼し、文字の明示送信と手動コピーを確認する
3. 画像、複数ファイル、フォルダーを一括にし、辞退・保存先指定・承認・サイズとハッシュ・空フォルダーを確認する
4. 同名、危険なパスとリンク、未対応項目、容量と並列上限、保存失敗、取消で、上書き・自動起動・実行がないことを確認する
5. 特定の相手と保存先だけに自動保存を設定し、一時停止・無効化・識別情報変更・信頼し直しで古い許可が復活しないことを確認する
6. ファイルを中断して先頭から再試行し、保存確認済みを再保存しないことを確認する。再起動後は新しい一括とし、別名コピーの可能性を示す
7. 狭い TCP 範囲を指定した相手に共有し、除外・予約ポート・未許可相手を検査する。範囲内で後から起動するアプリも期限まで対象になることを確認する
8. UDP とローカル待受の上限、競合、明示した番号対応、停止、期限、解除、片付けを試す
9. 相手側に sobalink がない通常の Tailnet サービスへ接続し、アプリの認証・TLS／ホスト鍵・実操作を確認する
10. 観測できる場合だけ直接・中継経路を記録し、回線中断とスリープ復帰を試す。不明を推測で埋めず、既存 TCP 維持を保証しない

通信準備、探索情報、ローカル一時保存は、アプリ成功や到着完了ではありません。停止してもデータ回収や遠隔ジョブ取消にはなりません。

## Tailcat の条件

**最初の版では利用できません。** サーバー・クライアントの鍵所有関係、認証済みペアリング、成功応答前の秘密状態の atomic 保存、信頼解除、UDP 多重化を先に解決します。必要な識別・切断 API を持つ固定した upstream を使用しますが、コンパイルや純粋な単体試験だけではペアリング成功を証明しません。

次に、明示した数値中継先と証明書ピン、別中継の capability 拒否、既定公開一覧・DNS bootstrap の不使用、必須ビルドタグ、未対応プロキシ・上書き環境の拒否を検査します。相手への直接通信と、選んだ中継先への暗号化ペイロード・HTTPS/ICMP 診断は許可範囲です。LAN 内だけ・外部通信ゼロとは説明しません。

ネイティブ環境の2台で、承認したペアリング、識別情報、転送とサービス、未許可相手の拒否、解除と終了、中継障害、直接・中継・再接続を実証します。任意の公開中継への代替接続や、方式の自動交換はしません。既存 TCP の継続は確認できた特定の条件と区別し、全般には保証しません。

## 公開と旧版

[配布手順](DISTRIBUTION.md)の正確なソース、ネイティブ、画面、反復ビルド、署名・provenance、公開取得、実導入の条件を満たします。ドラフト PR はリリースではありません。

旧 `tsnet-bridge` の公開版と実行記録は[Releases](https://github.com/webkaz-labs/tsnet-bridge/releases)にあります。実行ファイルと設定が異なるため、旧コマンドや RustDesk 固有の受入を現在の主手順として載せません。
