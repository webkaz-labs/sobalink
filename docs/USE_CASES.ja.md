# tsnet-bridge の活用案

更新日: 2026-10-01

tsnet-bridge を、必要なサービスだけをアプリやエージェントから使うための接続ツールとして広げる案です。**複数ポートをまとめる機能と、ローカルサービスへの逆向き接続**を加えると、SSH・Web への接続に加え、開発環境一式、AI API、複数端末エージェントの連携まで用途が広がります。必要な機能と実施順は [次期機能計画](ROADMAP.ja.md) を参照してください。

**本書は検討案です。記載したアプリとの互換性や、機能の実装・提供時期を保証しません。** 逆向き・汎用複数転送・タスク単位の制御は次期計画で、`0.1.0-alpha.2` には含まれません。現在の設定は RustDesk 向けで、以下の用途をそのまま利用できる状態ではありません。実装・試験の最新状況は [検証報告](VERIFICATION.en.md)、既存の利用手順は [README](../README.md) と [日本語手順](VERIFICATION.md) を参照してください。

## 現在の機能と拡張の境界

### 実装済みの接続基盤

- 独立した tsnet ノードによる対話認証とログイン状態の保存
- IPv4 loopback の固定 TCP／UDP 転送
- 認証必須の SOCKS5 TCP CONNECT。BIND と UDP ASSOCIATE は非対応
- 現在の tailnet ピアとポートの許可リスト、起動・停止・状態表示・診断
- `status --json` による現在のサービス全体の状態表示
- OS 全体の VPN・経路・DNS・プロキシ設定を変更しない構成

通信処理の自動試験と、実際のアプリの動作確認は別です。`ready` は TCP 到達確認を示し、アプリでの操作成功を示しません。

### 汎用用途に必要な一般化

現在の [設定](https://github.com/webkaz-labs/tsnet-bridge/blob/0069e38732227c8913ee6ceb0ec21784ae03d862/internal/config/config.go) と [サービス制御](https://github.com/webkaz-labs/tsnet-bridge/blob/0069e38732227c8913ee6ceb0ec21784ae03d862/internal/app/service.go) には、次の制約があります。

- RustDesk の公開鍵が必須
- 転送先は ID ポート、その直前のポート、relay ポートの組み合わせ
- 全ての設定済み TCP 転送先の疎通を確認してから待受を開始
- 転送先ポートにも 1024 以上の制約があるため、標準の SSH `22`、HTTP `80`、HTTPS `443` は設定不可

汎用化では、サービスごとに「転送先ピア・ポート・TCP/UDP・ローカル待受」を指定できるプロフィールが必要です。ローカル待受の権限制約と、リモート接続先のポート範囲を分け、RustDesk 固有の鍵・複数ポート・診断を専用プロフィールに残す形が候補です。現設定へ別用途の値を無理に当てはめる手順は提供しません。

### 次期計画で広げる接続基盤

- **名前付き複数転送:** Web・API・DB などをプロフィールにまとめ、必要な項目だけ有効化する
- **逆向き接続:** 許可した tailnet ピアから bridge の待受へ接続し、明示したローカルの loopback サービスへ届ける。TCP と UDP は別に設計・検証する
- **操作と安全性:** ピア選択、ポート提案、共有中の一覧、個別・全停止、TTL、失敗時に閉じる再接続、希望した場合だけの自動起動
- **エージェント向け制御:** ルール単位の JSON 診断、期限付きの準備待機、タスク単位の開始・取消・後片付け

逆向きは、通常の応答を返すことではなく、相手から新しい接続を受ける機能です。今まで localhost だけにあったサービスへ遠隔から届くようになるため、共有対象・相手・期限とアプリの認証を確認してから有効にします。

### 接続基盤とは別に必要な機能

ファイル・クリップボード同期、ジョブの割当や結果回収、stdio MCP の HTTP 化は、TCP/UDP 転送だけでは実現しません。ブラウザー向け HTTP プロキシ、独自のファイル受信サービス、GUI、無人環境の自動登録も別機能です。bridge は既存アプリやサービスを接続する基盤として扱います。

## アプリに指定するアドレス

同じポート番号を保つことと、相手の IP・名前へ直接接続できることは別です。用途ごとに、アプリの「接続先」と「プロキシ」の入力先を区別します。

| 接続方式 | アプリが使う接続先 | 別に指定するもの |
| --- | --- | --- |
| 固定の外向き転送 | 自分の `127.0.0.1` とローカル待受ポート | bridge 側に相手の tailnet ピアとサービスのポート |
| SOCKS 対応アプリ | 相手の tailnet ピア名または IP とサービスのポート | プロキシ欄に自分の loopback SOCKS 待受と認証情報 |
| 次期の逆向き転送を使う相手 | 提供側 **bridge ノード**の tailnet 名または IP と受信ポート | 提供側 bridge に明示した loopback 転送先、許可する相手、期限 |
| 通常の Tailscale を使うアプリ | 到達可能な相手の tailnet IP または MagicDNS 名とポート | 必要な tailnet 接続・ポリシーとサービス側の認証 |

固定転送でローカルとリモートを同じポート番号にしても、アプリの接続先はローカルです。相手の tailnet IP を指定するだけで bridge に流れる構成にはなりません。逆向きでも、利用側端末の `localhost` は提供側 PC を指しません。

bridge の設定に指定したピア名は、現在の tailnet ピア情報で照合します。これは OS の DNS に MagicDNS 名を登録する機能ではありません。SOCKS 利用時はアプリの認証対応と宛先名の渡し方も確認します。表は入力先の違いを説明するもので、現行 SOCKS の RustDesk 向け許可範囲や Chrome の認証制約を解消するものではありません。

## 逆向き接続と複数ポートで増える用途

以下は次期機能を前提にした構成例で、現在動作する設定例やコマンドではありません。

| 用途 | 想定する操作 | 必要なものと注意 |
| --- | --- | --- |
| Web/API/テスト DB の一括接続 | `web`、`api`、`test-db` を登録し、作業に必要な項目だけ開始 | 複数転送とグループ。DB を常に同時公開せず、認証と用途別権限を維持 |
| ローカル AI・テスト API の限定共有 | 提供側が loopback の対象と許可するピア・期限を選び、利用側へ入口を伝える | 逆向き TCP、アプリ認証。全インターフェースへ待受を広げず接続できる設計を検討 |
| 双方向のサービス連携 | それぞれが API や固定のコールバック先を必要な範囲で提供 | 両方向のルールと各側の承認。片方向の許可から逆方向の許可を推定しない |
| 期限付きの共同確認 | Web/API だけを一定時間有効にし、終了時にまとめて停止 | 逆向き転送の一覧・TTL・停止。相手が既に取得したデータは期限で回収されない |
| 自動処理・バックアップの接続 | 処理の間だけ必要な送受信サービスへ接続し、完了後に自分の転送を片付ける | タスク単位の制御。ファイル選別、同期、暗号化、重複防止、処理結果は各アプリが担当 |

例えば Web `3000`、API `8080`、テスト DB `5432` を名前付きで管理し、「Web と API のみ開始」「DB だけ停止」と扱う案です。ポートは一般的な説明例で、実サービスの有無や互換性を示しません。サービス間の URL、Cookie、CORS、認証は、複数のポートを開くだけでは整いません。

## AI エージェント向けの活用

### 認証付き HTTP MCP とローカルツール API

ローカルで動く認証付きの HTTP MCP/API を逆向き転送で提供し、許可した tailnet 上のエージェントから利用する構成です。対象サービスを選び、操作できる資源と相手を確認し、タスクに必要な期間だけ有効にします。

MCP の Streamable HTTP は HTTP のエンドポイントを使います。一方、stdio はクライアントが起動するサブプロセスの標準入出力を使うため、TCP ポートへ転送するだけでは利用できません。stdio 型しかないツールには別アダプターが必要です。利用するクライアント・サーバーの仕様版と認証方式を合わせて検証します。[MCP の公式トランスポート仕様](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)

**接続できる相手を絞ることと、ツールで何を実行できるかを絞ることは別です。** MCP/API 側の認証・認可を維持し、読み取り対象、書き込み、コマンドや引数を限定します。bridge が CLI の権限や承認を追加したり、ツールを自動で許可したりする構成にはしません。認証の宛先となる URL、TLS、origin も転送経路と合わせて確認します。[MCP 認可仕様](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)、[ツールの利用者確認](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

### 開発環境と遠隔 GPU の利用

エージェントのタスクに必要な Web・API・テスト DB を一つのプロフィールへまとめ、使うルールだけを開始する案です。別の認証済み推論 API を加えれば、GPU のある端末へ推論を依頼する構成も検討できます。データの送信先、DB の読み取り専用権限、API の利用上限は各サービス側で管理します。

ルール単位の JSON 診断と準備待機があれば、エージェントは「接続準備ができるまで待つ」「原因不明の障害なら実行を止める」「終了時に自分の接続だけ片付ける」という手順を組めます。現在の `status --json` は、これらのタスク単位の操作が実装済みであることを意味しません。

### 複数端末のエージェントをまとめて動かす

次は役割を分けた構成の例です。各サービス API は別途用意し、認証・許可された操作だけを受け付けます。

```text
オーケストレーター
  ├─ bridge の接続管理 → macOS のビルド用サービス API
  ├─ bridge の接続管理 → Windows のネイティブ試験用サービス API
  └─ bridge の接続管理 → Linux の GPU 推論用サービス API
```

1. 各実行環境の tailnet 接続と、サービスの利用権限を事前に確認する
2. タスクが所有する転送だけを開始し、タイムアウト付きで準備を待つ
3. オーケストレーターがジョブを割り当て、ジョブ ID と結果を管理する
4. 終了・取消時に実行側の状態を確認し、そのタスクの接続を片付ける

bridge が担当するのは接続の開始・状態・期限・停止です。スケジュール、並列数、成果物、実行の重複防止・再試行はオーケストレーターと各サービスが担当します。通信が切れても遠隔の処理が継続することがあるため、TTL や停止をジョブの取消と同一視しません。取消・結果照会の API と安全な再試行が別途必要です。

この構成は特権付きの任意コマンド実行口を提供する案ではありません。各端末のサービスには操作範囲・実行環境・資源上限を設けます。SaaS 上のエージェントは URL を知るだけでは tailnet へ入れず、対応する実行環境で承認された接続が必要です。また、bridge の許可リストはエージェントの他の OS 通信やファイルアクセスを隔離するものではありません。

## iPhone と iPad から使う

通常の Tailscale へ接続済みの iPhone/iPad を利用側にする構成も候補です。提供側の PC で次期の逆向き転送を有効にし、**iOS 側は Safari や対応する既存アプリから bridge ノードの tailnet 名とポートへ接続**します。この構成のために iOS 版 bridge を作る必要はありません。ただし、提供側の次期機能と実機での互換性確認が前提です。[Tailscale の iOS 対応](https://tailscale.com/docs/install/ios)

| 優先 | モバイルで試す用途 | 確認する点 |
| --- | --- | --- |
| 1 | 開発 Web 画面の実機確認・一時プレビュー | タッチ、画面幅、ログイン、WebSocket、期限切れ時の表示 |
| 2 | AI の Web UI・監視ダッシュボード | サービス認証、ストリーム表示、画面ロック後の復帰 |
| 3 | 既存のファイル Web サービス・SSH 対応クライアント | ファイル権限、アップロード範囲、SSH ホスト鍵、アプリの対応プロトコル |

- MagicDNS を使う場合は、iOS 側の Tailscale DNS 設定と bridge ノードの名前解決を確認します。端末本体の名前と bridge の独立ノード名を混同しません。bridge が OS の DNS や経路を自動修正する想定にはしません。[MagicDNS](https://tailscale.com/docs/features/magicdns)
- tailnet の暗号化と、ブラウザーが認める HTTPS の secure context は別です。遠隔の HTTP URL が localhost 扱いになるわけではなく、カメラ・マイク等を使う Web 画面には適切な HTTPS と利用者の許可が必要です。TCP 転送だけで証明書は用意されません。[getUserMedia の条件](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)
- Tailscale 接続後も各サービスのログイン・認可は必要です。iOS アプリにはバックグラウンド実行の制限があるため、Safari のタブ切替、画面ロック、回線変更を実機で確認し、常駐ジョブや長時間接続の維持を保証しません。[Apple のバックグラウンド実行](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time)

## 別の観点での候補

優先度は、上の接続基盤が検証できた後に用途ごとに判断します。新しい実行機能や LAN 接続を一括で追加する計画ではありません。

| 観点 | 活用案 | 境界・安全条件 |
| --- | --- | --- |
| コールバックの受信 | tailnet 上の別サービスから、ローカルのテスト用 API へ通知を返す | 公開 SaaS の webhook がそのまま届く入口にはならない |
| 限定した遠隔デバッグ | 認可済みのデバッグ接続を短時間だけ有効にする | コード実行につながる高権限の入口。強い認証・接続元制限・TTL を必須とし、無条件の自動再開を避ける |
| MQTT・IoT の確認 | tailnet ピアで動く broker/API へ接続する | 非 tailnet 機器には別途承認された gateway が必要。任意 LAN や自動発見を bridge が提供するわけではない |
| 障害時の確認 | 読み取り専用の状態・メトリクス API を必要な間だけ使う | 管理用の任意操作を許可せず、診断出力の秘密情報を除く |
| 環境の切替 | 同じローカル接続先を使うアプリで、確認後に対象プロフィールを切り替える | 接続先を常時表示。既存接続を無言で別環境へ付け替えず、証明書・ホスト鍵も環境ごとに検証する |

## 優先したい個別アプリ用途

以下は個別アプリ用途の検討順です。先に SSH/SFTP と単純 HTTP で汎用基盤を確認し、逆向き・複数ポート・エージェント連携へ広げる実施順は [次期計画](ROADMAP.ja.md) にまとめています。

| 優先 | 用途 | 主な拡張 |
| --- | --- | --- |
| 1 | SSH・SFTP・Git over SSH | 汎用 TCP 設定、接続情報の生成 |
| 2 | 開発画面・非公開ダッシュボード | 複数 TCP 設定、URL の保存と起動、必要に応じた逆向き提供 |
| 3 | 別端末のローカル AI API | 汎用 TCP と逆向き転送、相手側の接続・認証設計 |
| 4 | DB クライアント | 汎用 TCP 設定、接続先ごとの設定生成 |
| 5 | 端末間の定型処理 | 複数転送、項目別 JSON、準備待機、タスク単位の起動・停止 |
| 6 | RDP・VNC | 汎用転送、クライアント起動、実機検証 |
| 7 | ファイル・テキストの一時受け渡し | SFTP 利用、または独自の送受信機能 |
| 8 | 選んだ非公開サイトだけブラウザーで開く | HTTP プロキシ等とブラウザー連携 |

### 1 SSH と SFTP の接続補助

- **用途:** サーバー操作、ファイル転送、Git over SSH。
- **想定操作:** 保存した接続先を選ぶ → 転送を開始 → 表示された SSH コマンドや SFTP の接続情報を使う → 作業後に停止。
- **必要な拡張:** 汎用 TCP プロフィールと SSH 設定の生成。例えば、ローカル `127.0.0.1:2222` から選択した tailnet ピアの `22` へ転送する構成です。この構成は現設定では利用できません。
- **確認点:** SSH の鍵認証とホスト鍵確認を維持します。`HostKeyAlias` は転送先ごとのホスト鍵を管理する候補です。ProxyCommand を使う場合も補助プログラムの認証対応を確認します。OpenBSD `nc` のプロキシ認証は HTTP CONNECT のみで、よくある `nc -X 5` の例を本ツールの認証必須 SOCKS へそのまま適用できません。[OpenSSH](https://man.openbsd.org/ssh_config#HostKeyAlias)、[OpenBSD nc](https://man.openbsd.org/nc#P)

### 2 開発画面と非公開ダッシュボード

- **用途:** 開発サーバー、監視画面、管理画面など、tailnet から到達できる Web サービス。
- **想定操作:** 「開発画面」などの登録名を選ぶ → 到達を確認 → ローカル URL をブラウザーで開く。
- **必要な拡張:** 汎用 TCP 設定、URL の保存・表示・起動。最初は単一ポートの HTTP サービスで確認し、複数ポートで Web/API をまとめます。localhost だけのサービスを相手に見せる場合は逆向き提供を使う計画です。
- **確認点:** ログイン、絶対 URL、リダイレクト、WebSocket、Cookie、Origin の検査を含めて試験します。HTTPS を localhost の URL に置き換えるだけでは、証明書名やアプリの origin が変わります。証明書警告の回避や検証無効化を通常手順にしません。[curl の証明書検証](https://curl.se/docs/sslcerts.html)

### 3 別端末のローカル AI API

- **用途:** 推論用の端末で動く API を、別端末の対応アプリから利用。
- **想定操作:** 登録済みの AI 接続先を選ぶ → 到達を確認 → 接続先 URL を対応アプリへ入力。
- **必要な拡張:** 汎用 TCP 設定と、提供側の loopback サービスへ届ける逆向き TCP。モデル一覧や API の応答確認は追加の補助機能として検討できます。
- **確認点:** Ollama は既定で `127.0.0.1:11434` を待受し、ローカル API は認証不要です。逆向き転送を使う場合も、遠隔からこの API に届く点を考慮し、接続元の限定と認証付きゲートウェイ等の必要性を検討します。現行のクライアント側 bridge だけで相手の localhost へ到達できるわけではなく、提供側にも次期の逆向き機能または別の適切な接続経路が必要です。[Ollama の待受設定](https://docs.ollama.com/faq#how-can-i-expose-ollama-on-my-network)、[API 認証](https://docs.ollama.com/api/authentication)

### 4 DB クライアントの接続補助

- **用途:** PostgreSQL などを既存の CLI・GUI クライアントから利用。
- **想定操作:** DB の接続先を選ぶ → 専用のローカルポートを確認 → DB クライアントで通常の認証を行う。
- **必要な拡張:** 汎用 TCP 設定、接続先ごとのポート管理と接続情報の表示。
- **確認点:** DB 認証・権限・TLS 検証は維持します。確認作業なら読み取り専用アカウントを優先します。トンネルがあることを理由に認証を無効化せず、接続先名を変更した場合は DB クライアントの証明書検証も確認します。[PostgreSQL の接続認証](https://www.postgresql.org/docs/current/auth-pg-hba-conf.html)

### 5 端末間の定型処理

- **用途:** バックアップ先への転送、処理結果の取得、非公開 API や MQTT への接続。
- **想定操作:** 認証済みのプロフィールを指定 → 転送を開始して定型処理を実行 → 結果を返して、その処理のために起動した転送を停止。
- **必要な拡張:** 名前付き複数転送、項目別 JSON、準備待機と、処理の終了・中断・失敗に連動するタスク単位の起動管理。既に利用中の転送を誤って停止しない設計も必要です。
- **確認点:** 現在は対話認証が前提で、認証キー等による無人登録は提供していません。CI の一時実行環境へ自動登録する用途には、別の認証・失効・秘密情報管理の設計が必要です。任意のリモートコマンド実行機能まで初期範囲へ広げません。

### 6 RDP と VNC の接続ランチャー

- **用途:** 登録した遠隔画面へ既存クライアントで接続。
- **想定操作:** 接続先を選ぶ → 必要な転送を開始 → 接続情報を表示、または対応クライアントを起動。
- **必要な拡張:** 汎用 TCP／UDP 設定とクライアント連携。
- **確認点:** 認証、証明書、UDP の利用、表示・入力・再接続・転送性能を実機で確認します。ポートが到達可能であることだけでは互換性を主張しません。

### 7 ファイルとテキストの一時受け渡し

- **用途:** 選んだファイルや短いテキストを、指定した相手へ明示的に送る。
- **想定操作:** 送信対象と宛先を選ぶ → 送信内容を確認 → 受信側が受け取る。
- **必要な拡張:** 既存 SFTP の利用なら案 1 の延長です。次期の逆向き転送で既存の受信サービスを接続することは検討できますが、bridge 自体がファイル送受信アプリになるわけではありません。独自のドラッグ＆ドロップ、受信確認、ファイル単位の期限付き共有には受信側サービスと UI が別途必要です。
- **確認点:** 保存先、上書き、容量上限、中断、宛先確認が必要です。テキスト送信は明示操作を基本とし、自動クリップボード同期は別途の検討対象とします。

### 8 選んだ非公開サイトだけブラウザーで開く

- **用途:** 登録したサイトだけを bridge 経由にして、通常の閲覧と併用。
- **想定操作:** サイトを選ぶ → 専用のブラウザー設定で開く → 対象サイトだけを許可した経路へ送る。
- **必要な拡張:** 認証付き HTTP プロキシ／CONNECT 等と、対象 URL を選別するブラウザー連携。現在の SOCKS 設定だけでは実現しません。
- **確認点:** Chrome は SOCKS5 のユーザー名・パスワード認証に対応しないため、本ツールの認証必須 SOCKS へ直接接続できません。SOCKS5 の対象名解決は Chrome ではプロキシ側ですが、これだけでブラウザーの全通信が隔離されるわけではありません。対象サイトでプロキシが失敗した場合に直接接続へ戻さないこと、DNS、リダイレクト、WebSocket、外部リソースも確認します。[Chromium のプロキシ仕様](https://github.com/chromium/chromium/blob/main/net/docs/proxy.md#socksv5-proxy-scheme)

## 共通の安全性と互換性

- **外向きの接続先は現在の tailnet ピアに限定します。** 任意の LAN アドレスやサブネット経路への転送はありません。相手の localhost へ届ける案には、提供側で明示したサービスだけを受け付ける逆向き機能が別途必要です。
- **逆向き転送はアクセス範囲を広げます。** 接続元、サービス、期限を明示し、保存だけで有効にしません。アプリからの接続元が loopback に見えることで、ローカル用の認証省略が遠隔にも適用されないか確認します。
- **固定転送はアプリの隔離機構ではありません。** 他のローカルプロセスも loopback 待受へ接続できます。SOCKS の認証も固定転送には付きません。tailnet の最小権限とアプリ側の認証を併用します。
- **転送により接続元の見え方が変わります。** 相手のアクセス制御・監査で、元アプリの端末アドレスがそのまま見えるとは仮定しません。
- **名前を保持すべきプロトコルを区別します。** HTTPS の証明書名・SNI、Web の origin、SSH のホスト鍵を確認します。CLI で HTTP(S) を試験する場合、curl の `--connect-to` は接続先だけを変更し、TLS とアプリで使う元の名前を保持する選択肢です。[curl](https://curl.se/docs/manpage.html#--connect-to)
- **UDP 転送は LAN の再現ではありません。** 逆向き UDP は TCP と別に設計・試験します。固定 UDP があっても、SOCKS UDP、mDNS・ブロードキャストによる自動発見、任意の動的ポート交渉にはなりません。
- **資格情報と診断内容を公開しません。** ログイン URL、保存状態、SOCKS 資格情報、実際の接続先情報を共有用設定やログへ含めないよう確認します。詳細は [セキュリティ](../SECURITY.md) を参照してください。

## 通常の Tailscale との使い分け

**通常の Tailscale と既存機能で目的を満たせる場合は、まずその構成を使うのが簡潔です。** 一般的な通常クライアント構成では、アプリから tailnet IP や MagicDNS 名へ直接接続でき、到達可能なサービスごとにローカル転送を作る必要がありません。接続元・宛先・ポートの制限は通常の Tailscale の ACL/grants でも可能です。[MagicDNS](https://tailscale.com/docs/features/magicdns)、[アクセス制御](https://tailscale.com/docs/features/access-control/grants)

ローカルサービスを tailnet へ提供する機能も既に **Tailscale Serve** にあります。HTTP(S) や TCP 転送、複数の TCP ポート設定、JSON 状態表示があり、逆向き提供や複数ポート自体を bridge 固有の利点とはしません。Serve の HTTPS 設定・証明書発行等に必要な同意は別に確認します。[Serve](https://tailscale.com/docs/features/tailscale-serve)、[CLI](https://tailscale.com/docs/reference/tailscale-cli/serve)、[複数ポートを保持する設定](https://github.com/tailscale/tailscale/blob/v1.102.5/ipn/serve.go)

| 比較点 | 通常の Tailscale と Serve | 現在の bridge | 次期 bridge で目指すもの |
| --- | --- | --- | --- |
| 接続の入口 | OS の tailnet 経路を使い、対応アプリから直接接続 | 選んだ通信を loopback 転送／認証付き SOCKS へ送る | 名前付きルールを用途別にまとめて操作 |
| サービスの提供 | Serve などの既存機能を利用可能 | tailnet 側の受信待受なし | 独立 tsnet ノードから、明示した loopback サービスへ逆向き転送 |
| 操作のまとまり | 既存 CLI・設定・スクリプト等で管理 | RustDesk 固有の一つのプロフィール | 複数ルールの個別有効化、グループ、対象と期限の一覧 |
| タスクとの連携 | 状態取得や既存機能を組み合わせる | サービス全体の JSON 状態 | 準備待機、タスクごとの所有関係、取消時の後片付けを共通化 |
| 許可範囲 | tailnet の ACL/grants とアプリの認証 | tailnet 制御に加え bridge の宛先許可リスト | 逆向きの接続元制限も追加。アプリの操作認可は別途維持 |

tsnet の利点は、独立したノードをプロセス内に持ち、bridge 自身が OS 全体の経路・DNS を変更せずに動くことです。次期 bridge ではさらに、「この作業で使う接続だけをまとめて開始し、状態を確認し、終了時に片付ける」という操作を揃えることに価値を置きます。通常の Tailscale でもスクリプト等で組める用途はあり、独占的な機能とは扱いません。[tsnet 公式資料](https://tailscale.com/docs/features/tsnet)

導入時は次の負担も比較します。

- 既存 Tailscale とは別の認証・ノード・保存状態が増え、ポリシーとプロフィールの管理が必要
- ローカルポートの競合、URL や TLS 名の扱い、アプリごとの接続設定が増える場合がある
- tsnet を使うだけで安全性が上がったり、他の OS 通信やファイルアクセスを隔離できたりするわけではない
- 管理者権限を要求しない設計と、Windows 標準ユーザーでの実機検証完了は別。現在は後者が残っている
- 常駐、電池消費、CPU・メモリー、転送速度、direct／DERP 経路の影響を測定する必要があり、通常の Tailscale より軽量・高速とは主張しない

多くのアプリから常時接続したい場合や、Serve で localhost の共有が足りる場合は、通常の構成の方が管理を減らせる可能性があります。bridge は、独立ノードと作業単位の接続管理がその追加負担に見合う場合の選択肢です。

## 検討する順序

1. 汎用の名前付き複数転送・グループと、ルール単位の状態表示を整える
2. SSH・SFTP と単純 HTTP で外向き接続を検証し、逆向き TCP を接続元制限・停止・期限とセットで設計する
3. 逆向き UDP は別途検証し、AI/API・DB の組み合わせや双方向連携を確認する
4. タスク単位の準備待機・後片付けを加え、認証済みのサービス API を使ったエージェント連携を検証する
5. 自動起動は希望制とし、ブラウザープロキシや独自ファイル・同期アプリは別の拡張として扱う

共通の操作は「対象と相手を選ぶ・必要な項目だけ開始する・接続情報をコピーする・状態を確認する・停止する」を基本とします。具体的な依存順と合格条件は [次期機能計画](ROADMAP.ja.md) を参照してください。既存アプリの設定を書き換える場合は、事前の表示、明示的な選択、復元方法が必要です。
