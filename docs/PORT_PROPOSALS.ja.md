# 代替ポートの明示的な確認

[English](PORT_PROPOSALS.en.md) · [CLI ガイド](CLI_GUIDE.ja.md) · [容量](CAPACITY.ja.md) · [API](../web/API.md)

停止中の保存済み送信 TCP/UDP 接続は、代替のローカル入口ポートを明示的に確認できます。別途確認した保存・再開始操作までは、元の固定ポートを維持します。ローカル Web UI では、停止中の接続の「保存済みサービス → サービスを管理 → 代替ポートを確認」を開きます。画面を開くだけでは元設定の読込みのみを行い、「ループバックポートを今確認」で一時的な待受を明示的に確認します。

```sh
soba service show NAME_OR_ID
soba service ports NAME_OR_ID
soba --dry-run service restart NAME_OR_ID --local-port PORT --expected-revision REVISION
soba service restart NAME_OR_ID --local-port PORT --expected-revision REVISION
```

Web 画面には元設定の正確な ID・版、プロトコル、ループバックの系統、元の対応、有効なリモートポート、除外と確認時刻を表示します。候補数・回数の入力が0なら現在の有限の容量設定に従い、待受回数と期限は「設定 → 容量と履歴」で変更できます。候補一覧のページ移動では追加の確認をしません。候補を明示的に選び、「選んだポートで下書きを編集」へ進みます。保存済み定義の編集画面は元設定を再読込し、版が変わっていれば候補を反映せず拒否します。停止状態の定義全体を確認して別途保存し、開始も別の確認操作で行います。元設定の再読込では候補を破棄し、新しい版へ自動反映しません。閉じる・元設定の変更・接続状態の喪失では、処理中の結果を破棄します。観測には毎回新しい要求 ID を使い、変更操作の再試行ガードとは分離します。

`service ports` が返す版と選んだポートを使い、一連の操作で同じ `--state-dir` を指定してください。再開始前に保存済み設定全体と有効期間を確認します。通常の明示的な再開始では、確認した許可の有効期間が新しく始まります。稼働中サービスは先に明示的に停止してください。共有やアプリ側の接続先ポートは、この候補提示の対象外です。

最初に保存済みの数値ループバックの対応を確認し、OS が「アドレス使用中」と報告した場合だけ別の候補を調べます。元の対応が現在利用可能なら `listener_no_conflict` を返し、自動再開始しません。選んだ TCP/UDP と正確な `127.0.0.1` または `::1` の系統で一時的に待受を試します。ソケットでアプリの通信を受理・転送せず、結果を返す前にすべて閉じます。保存済み設定、相手への許可、自動起動の承認、ルーターやセキュリティ設定は変更しません。

## 対応と再確認

候補は高位ポートだけを使い、既知のアプリ・管理画面・プロキシ・バックエンドの予約ポートを除外します。保存済みのプロトコル、ループバック系統、有効なリモート範囲全体を維持します。通常の `connect --local-port` と同じく、連続したローカルポートを、除外後のリモートポートの昇順に対応させます。例えばリモート `8000-8002` から `8001` を除外すると、ローカル `49152-49153` はリモート `8000,8002` に対応します。結果には元の設定全体と版を含み、元の固定ポートの意図も確認できます。

候補は予約でも将来の利用保証でもありません。直後に別のプロセスが利用する場合があります。別の明示的な再開始操作は各待受を再確認し、失敗時は既存の全入口のロールバックを使います。開始に失敗しても、明示的に選んだ保存済み設定を残し、別のポートへ切り替えません。`--expected-revision` は候補確認後の設定変更を拒否し、古い確認を最新の許可へ読み替えません。開始時には現在のバックエンド、相手の ID、共有サービスの確認、容量も検査します。

## 有限で変更できる確認量

`--from-port PORT` は1024〜65535の開始位置です。既定は49152です。`--count N` は候補数、`--attempts N` は候補範囲の確認回数を指定します。省略または0なら、対応する有限の容量設定に従います。

- `portProposalResults`: 既定は候補3個
- `portProposalAttempts`: 既定は候補範囲32回。予約ポートによる除外も含む
- `portProposalBinds`: 元の対応も含め、待受確認の合計は既定で4096回
- `portProposalSeconds`: 確認の期限は既定で5秒。サービスの許可期間とは独立
- `materializedListeners` の残容量: 確認中に同時に保持するソケット数の上限

通常の容量の確認・適用フローで、これらの値を増減できます。正の要求数は選んだ容量内に収めます。ポートの表現範囲から、高位の開始位置は最大64512個です。確認量と結果数は有限であり、サービスの許可期間とは別です。大きな対応範囲には、範囲全体を確認できる同時入口数と待受確認の容量が必要です。確認の期限は設定の事前確認前から始まり、バックエンドの状態読込みも含みます。正規化済みの除外走査は線形で、解析・正規化の量はポートの表現範囲で制限します。一貫した確認のため本体のコマンドロックを保持します。取り消し・期限超過では途中のソケットを閉じ、共通のエラーを返し、候補の結果は返しません。

`stopReason` は `requested_count`（要求候補数）、`attempt_budget`（候補範囲の回数）、`bind_budget`（待受確認の容量）、`port_range`（ポート範囲の末尾）のいずれかです。候補が少なくても、他の全ポートが使用中とは限りません。別の高位の開始位置を指定するか、有限の容量を確認してください。`--dry-run service ports ...` は待受せず予定を表示します。`--json` の形式と値は日本語・英語で共通です。この観測結果は要求の重複除去キャッシュに残しません。同じ要求 ID の再送でも、新たに明示的な確認を行います。選んだ有限の候補数とポートの表現範囲が1結果の大きさを制限し、CLIの応答にはローカルIPCのサイズ制限も適用します。Web側は、この制約付きの結果全体を解釈し、別の生応答バイト上限は設けていません。応答・解釈の失敗はエラーであり、途中の候補を利用可能な結果として返しません。

## 確認できた失敗

| コード | 意味と次の操作 |
| --- | --- |
| `listener_conflict` | OS のアドレス使用中。候補を明示的に確認するか競合元を停止 |
| `listener_no_conflict` | 元のポートは現在利用可能。代替の選択・開始は行っていない |
| `listener_capacity` | 同時入口数の設定、または OS の記述子・メモリー・ソケット容量が不足。ポート変更では解決しない |
| `listener_probe_timeout`, `listener_probe_canceled` | 明示的な確認の期限超過・取消。保存済み設定は不変。確認量を見直して明示的に再試行 |
| `listener_probe_capacity` | 確認要求が有限の容量を超過。確認用の容量を見直す |
| `listener_permission_denied` | OS の待受権限で拒否。自動的な権限昇格やセキュリティ変更はしない |
| `listener_address_unavailable` | 選んだループバックの系統・アドレスが利用不可。明示的な選択を確認 |
| `listener_mapping_invalid` | プロトコル・ループバック・ポート・除外・高位ポート対応の範囲が不正 |
| `listener_unavailable` | 分類できない待受の失敗。原因は不明のまま扱う |
| `listener_proposals_exhausted` | 制限した検索内で候補なし。システム全体の空き状況は断定しない |

既存の認証、稼働中、対象なし、バックエンド、版の失敗は別に扱います。確認結果はローカル管理用で、相手には配信しません。合成データと実際のループバックを使う自動検査だけでは、アプリの互換性、実際の登録、OS ログイン・サスペンドの受入は完了したと判断しません。
