# ローカル転送設定リソース: ソースビルド

[English](RESOURCE_SETTINGS.en.md) · [使い方](GENERIC.ja.md)

このソースは転送の受付制限2項目について、ローカルの内容確認・変更案の確認・確認内容に結び付いた適用・永続的な操作記録を提供します。ソースビルドの機能であり、新しい公開版の案内や公開の確約ではありません。遠隔管理や Web UI のリソース操作は追加しません。

## 確認・適用・結果照会

ローカルの本体を起動し、別の端末ウィンドウで同じプロファイルを指定します。[コマンドの手順](GENERIC.ja.md#ローカル転送設定の操作ソースビルド)に従い、一覧取得、両項目の preview、結果の確認、正確な確認内容での apply、必要に応じた status の順に進めてください。

`list`・`inspect`・`preview`・`apply`・`status` は言語によらず安定した JSON を返し、明示的な `--json` も使えます。CLI の `status` は `resource.operation.status` を送ります。ヘルプとエラーは `--locale auto|ja|en` に従います。`list` が返した正確な不透明 ID を使ってください。両項目とも `default` または 9007199254740991 以下の正の有限整数が必要です。`unlimited`・ゼロ・負数は拒否します。提供側でも容量設定全体の変更案を検証します。`requested` は指定値、`effective` は解決後の値です。制限を下げても進行中の転送を中止せず、新規受付に反映します。

preview は設定変更・転送開始・操作枠の予約を行いません。共通オプション `--dry-run` は本体に接続せず入力検査と要求の表示だけを行い、現在の状態の検証や正式な変更確認はしません。共通オプション `--offline` による停止中の設定編集は非対応です。`start --offline` で起動した本体では、保存済みネットワークを開始せずローカル設定を操作できます。

## 変更確認の失効と再試行

- apply には preview の正確な `operationId`・`baseRevision`・`revision` と確認済みの両項目が必要です。暗黙の preview や現在の revision への置換は行いません。指定値を変える場合は新しい変更案を確認してください。
- 変更確認は現在の設定・プロファイル、正確な指定値、ローカルの主体・操作、プロセスの権限状態の revision、次の操作枠に結び付きます。権限状態への書込み試行は、失敗や変更後の復元も含め、安全側に確認を無効にします。別の操作が受け付けられると操作枠を消費します。再起動後の新しい操作には新しい確認が必要です。失効は状態に基づき、時刻によるタイムアウトではありません。
- 複数の preview が同じ未予約の操作枠を返す場合があります。その ID を使えるのは受け付けた確認内容だけです。保持中の要求と内容が異なる場合は `resource_operation_mismatch`、現在の状態や操作枠に対して古い場合は `resource_revision_conflict` を返します。新しい操作の前に現在の内容と新しい変更案を確認してください。
- 保持中の記録は起動世代・revision より先に検査します。同じ操作 ID と同一の確認内容での再試行は、再起動後も過去の記録を返し、設定処理を再実行しません。応答が失われた場合は `status` を確認してください。応答がないことを、新しい操作で黙って置き換える理由にしないでください。
- 削除済み・消費済みの操作は `resource_operation_not_retained` となり、再実行できません。`resource_operation_not_found` は保持中の実行結果が不明であることを示します。どちらも成功・失敗の証明ではありません。ローカル操作の要求 ID は、この永続的な操作 ID とは別です。

## 操作結果と現在の状態

操作の応答には `operationId`、過去の `outcome`、`evidenceDurable`、別の `current` 記述子、`journal` 使用量があります。現在の記述子は応答時点の観測値です。従来のコマンドや後続の操作で設定が変わり、過去の要求とは異なる場合があります。過去の成功は、その設定が現在も有効であることを意味しません。

| `outcome.status` | 意味 |
| --- | --- |
| `applied` | 設定を確実に保存し、必要な使用量管理・転送の段階が成功した |
| `saved_not_applied` | 設定を確実に保存したが、使用量管理または実行時の転送設定への反映に失敗した |
| `failed` | 設定変更を試みなかった、またはファイルを公開できず、実行時の段階も試みなかった |
| `canceled` | 操作予定を確実に保存した後、設定適用の前に取り消しを検出した |
| `unknown` | 設定の永続化が不確か、操作予定が未完了などのため結果を確定できない |

`outcome.configuration` は `durable`・`not_attempted`・`not_published`・`uncertain`・`unobserved` のいずれかです。`outcome.accounting` と `outcome.transfer` はそれぞれ `succeeded`・`not_required`・`failed`・`not_attempted`・`unobserved` のいずれかです。固定の列挙値に提供側の生のエラーは含めません。`unknown` は成功も巻き戻しも意味しません。`evidenceDurable: true` は結果を確実に記録したことを示しますが、その結果自体が不確かさを記録している場合もあり、適用成功の証明ではありません。操作予定の受付前に取り消された場合は、操作記録を作らずコマンドの取り消しエラーを返すことがあります。

## 記録の上限と復旧

非公開の操作記録には、128件かつシリアライズ済み全体で256 KiB（262144バイト）の固定上限があります。設定処理の前に完了後の記録用容量を確保するため、128件より前にバイト数の上限に達する場合があります。`journal` は `records`・`bytes`・`maxRecords`・`maxBytes`・`writable` を返します。`writable` は不確かさによって受付を停止していないかを表し、保存先や空き容量が利用できる保証ではありません。

操作予定・正本の設定・操作結果は別々の書込みであり、複数ファイルをまとめたトランザクションではありません。設定処理の前に操作予定を確実に保存し、その後に結果を書き込みます。結果が判明した完了記録は上限内で古い順に削除できますが、未完了の操作予定と結果不明の操作は保持し続けます。自動再実行や強制削除では解決しません。保持必須の記録だけで容量を使い切った場合、新しい操作は `resource_journal_full` となります。

操作予定の書込みでファイルを公開できなかった場合は、設定変更を試みず `resource_journal_write_failed` を返します。操作予定の公開が不確か、または結果の書込みが失敗した場合は、不明の記録を返して新しい適用を停止します。後の所有者による起動で、ディスク上の記録を検証して確実に再保存してからリソースを有効にします。設定操作の再実行はしません。起動時に記録の確実性を確認できなければ、リソースは利用不可のままです。status や現在の状態の観測だけで不明の結果を自動修復することはありません。

これは上限付きの記録と再実行しない仕組みであり、厳密に1回の実行、複数ファイルの巻き戻し、実際の電源断からの復旧を保証しません。ローカルの番号ではプロファイル全体の巻き戻しを防げません。ID の復旧や保持必須の記録を空けるために非公開の保存状態を削除しないでください。

## ID・互換性・対象範囲

- 対象は `transfer-admission-settings` 型の1リソースです。権限主体と提供側はローカル範囲で、不透明な永続 ID を持ちます。ID は端末名・パス・アドレス・相手の識別子ではありません。非公開の保存ディレクトリー全体を複製すると ID も複製され、遠隔で複製を解決する機能はありません。
- 対象項目は `transferConcurrentFiles` と `transferConcurrentPerPeer` だけです。正本は既存の容量設定で、無関係な設定と従来のプロファイル・容量ファイル形式を維持します。
- 所有権を確保した起動処理が上限付きの非公開リソース記録を検証し、再保存します。破損・非対応・不確かな状態では ID を勝手に作り直さずリソース機能を無効にし、従来の設定は維持します。操作記録が入った状態で以前の PR1 読み取り専用実装に戻すとリソースの操作口は利用不可になりますが、従来の設定は継続します。
- 応答に非公開パス・相手一覧・通信の識別子・プロファイル全体は含めません。固定のローカル主体は個人の識別子ではありません。既存の認証付きローカル操作を使います。CLI はローカル IPC を使い、既存のローカル Web `/api/command` からも同じコマンドを利用できます。認証と Fetch Metadata の保護は変更しません。固定の `local-control` は両方の入口を表し、個人を識別しません。新しい Web UI の操作部品・相手向け管理接続口・管理権限・探索の広告は追加しません。ペアリングは管理権限を与えません。

モック試験は上限付きロジックの確認に限られます。実端末の受入確認、実際の電源断に対する耐久性、公開配布物の受入確認は別です。[開発原則](DEVELOPMENT_PRINCIPLES.ja.md)と[安全性の境界](../SECURITY.md)も参照してください。
