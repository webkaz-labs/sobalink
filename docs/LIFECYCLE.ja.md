# 起動と Tailnet ログアウト

[English](LIFECYCLE.en.md) · [利用ガイド](GENERIC.ja.md)

`soba` と `soba run` はフォアグラウンドで動作します。`soba start --background` は本体をバックグラウンドで起動し、ローカル管理機能の準備を待ちます。起動成功はローカル管理機能の準備を示し、ネットワーク接続や他のアプリの動作成功までは示しません。`soba status` で状態を確認し、`soba ui` で新しいログインコードを取得します。

## 起動時に復元されるもの

| 状態 | 通常起動 / `--startup saved` | `--offline` / `--startup offline` |
| --- | --- | --- |
| ローカル管理画面・CLI | 起動 | 起動 |
| 明示的に保存した Tailnet / LAN | 起動。認証・ペアリングが必要な場合あり | 起動しない |
| 保存済みの相手の許可 | 選択したネットワークで復元 | 保存したまま。ネットワーク受信なし |
| 相手ごとのファイル自動保存 | 選択したネットワークで、有効かつ一時停止中でない許可を復元 | 受信なし |
| 通常の保存済み共有・転送用入口 | 停止したまま | 停止したまま |
| 別に許可した外向き起動時接続・プロキシ | ネットワーク準備後、確認した正確な範囲を一度だけ開始 | その本体の起動中は抑止 |
| 前回のファイル転送 | 再開しない | 再開しない |

自動保存は承認済みの相手と保存先の組み合わせに限ります。既定の受信フォルダーを設定しただけでは、自動保存を許可しません。ファイルを自動で開いたり実行したりしません。オフライン起動でも許可は削除されず、後でネットワークを明示的に有効化すると保存済みの受信許可が有効になります。

Ctrl+C、`soba stop`、画面の停止操作は、保存済みログインを維持して本体と通信を停止します。バックグラウンド起動を繰り返すと `already-running` と `startupApplied: false` を返し、稼働中の本体の起動方式は変えません。方式を変更する場合は先に停止してください。

バックグラウンドのアプリ出力とコマンドエラーは、選択した状態ディレクトリ内の非公開 `startup.log` に保存します。本体の動作中もこの1ファイルを1 MiB以下に保ち、古い内容を除いて直近の出力を残します。上限に達すると直近の最大半ファイル分を残して追記し、1回の出力が上限を超える場合は末尾の1 MiBだけを保存します。保存内容の先頭行は途中から始まることがあります。バックアップログは蓄積しません。ランタイムのパニック出力を含む、プロセスの標準出力・標準エラーへの直接出力は、バックグラウンド起動では破棄します。フォアグラウンドの `soba run` は従来どおり端末に診断を表示します。サインイン時起動のサービス管理ログは、別途OSが管理します。

準備確認がタイムアウト・中断しても本体が動作している場合があります。再試行前に `soba status` を確認し、必要なら `soba stop` を使います。起動エラーやランタイムのパニックを直接確認するには、同じ `--state-dir` で `soba run` を実行します。

別の任意許可は[明示的な起動時接続・非公開SOCKS設定](STARTUP.ja.md)で説明します。定義保存・取込みだけでは起動許可を作りません。確認した範囲・ネットワーク・ホスト名の変更や相手の許可取消しで古い許可は無効になります。有限期間は新しいオンライン起動で新たに始まり、既存接続の復旧では延長しません。受信共有と過去のファイル転送は自動開始しません。

## サインイン時の任意の自動起動

まず計画を表示します。

```sh
soba autostart enable --startup saved
# 保存済みネットワークを開始せず、ローカル管理のみ起動する場合:
soba autostart enable --startup offline
```

プレビューには登録ファイル、サービス管理コマンドの正確な引数、保存済みネットワーク、起動後に自動保存が有効になる承認済み相手と保存先を表示します。`saved` では別に許可した外向き起動時接続と保存プロキシも開始対象になります。OSサインイン時起動を有効にする前に `soba startup list` と `soba proxy saved` を確認してください。登録だけではその許可を作らず、サービス共有は手動のままです。確認対象は現在の保存済み設定です。その後に明示的に設定を変更した場合は、変更後の設定が次回起動に適用されます。

確認後、同じ操作・方式で `--apply --review TOKEN` を付けて再実行します。`TOKEN` は表示された `reviewToken` に置き換えます。`--json` で機械向けのプレビュー・結果を取得できます。トークンは OS ごとの計画と保存済み設定全体を対象とし、変更があれば再確認が必要です。表示・登録時には本体の即時起動やノード登録を行いません。

Linux は systemd のユーザーユニット、macOS は LaunchAgents、Windows は対話ユーザーの最小権限タスクを使います。管理者権限やマシン全体のサービスは使いません。次回以降のサインイン向けの登録であり、解除しても稼働中の本体は停止しません。

解除は `soba autostart disable --startup saved`（元の方式が `offline` なら同じ方式）を表示し、そのトークンで適用します。解除までは元の実行ファイルの場所を維持してください。登録ファイルの内容が変わっていた場合は拒否します。方式や実行ファイルの場所を変えるときは、先に一致する旧登録を解除します。Windows の既存タスクは強制置換しないため、有効化に失敗した場合は既存タスクを確認してください。

## Tailnet からのログアウト

```sh
soba logout
```

保存済みの Tailnet ネットワークを有効にしてから使います。まずローカルのサービス、相手向け待受、ファイル転送を停止し、その後で組み込みノードへログアウトを要求します。どちらの結果でも本体を終了します。

- 成功時の `state: logged-out` と `logoutConfirmed: true` は、ローカルのバックエンドがログアウトを受理したことを示します
- `tailnet_logout_unconfirmed` はバックエンドでのログアウトが未確認です。通信の停止を確認できたか、終了処理も未確認かはエラーに表示します。転送の停止が完了しなければ、バックエンドへのログアウトは試行しません。本体の終了を待ってから保存済み Tailnet で起動し、再試行します
- `logout_cleanup_unconfirmed` はログアウトを確認したものの、待受の終了処理にエラーがあります。再起動前に本体が終了したことを確認します

ログアウトは保存済みの相手の許可・サービス定義・ファイルを削除しません。Tailnet 管理画面からのノード削除は別の管理操作です。LAN のペアリングには明示的な LAN 解除操作を使い、Tailnet ログアウトは使いません。

## 検証の範囲

自動テストは注入したバックエンド、メモリー内の相手との接続、一時ディレクトリ、模擬サービス管理処理を使用します。通信停止の順序、ログアウトの確認・未確認、起動の繰り返し、早期終了・中断、確認後の計画変更、エスケープ、3 OS のユーザー単位の登録内容を検証します。OS への実際のサインイン・サスペンド、インストール後の実行ファイルからの起動、実登録、他アプリとの互換性を確認したものではありません。実機での受入確認は別途必要です。
