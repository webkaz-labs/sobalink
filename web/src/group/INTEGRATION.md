# Fixed-group transfer settings Web integration

Source implementation and synthetic tests are prepared. This new integration has not yet passed its independent frozen execution gate. Earlier settings/catalog/navigation receipts do not cover it. See the final gate receipt for the exact tested state before making a completion claim.

One App-lifetime `ResourceGroupController` shares `ResourceAttemptRegistry` with the existing single-device controller. Seven exact local commands are typed: preview, review.select, review.current, apply, status, status.refresh and cancel. They use the existing authenticated `api.command` adapter, a fresh request ID and AbortSignal; they never enter `useServer.run`, an effect, a retry queue or polling. The existing transport body and error/retry behavior remain unchanged.

The generic Group transfer settings navigation is ordinary UI. Saved public keys label fixed 1–16 member choices; exact resource/grant/revision inputs remain advanced. An already selected W1 Management v2 selector can be explicitly copied into the draft. A group member can navigate to the inert single-device selector screen and back. None of these navigation actions invokes transport or obtains a grant. Inspection v1 and the local device cannot join a group.

Every draft has both template fields. Overrides distinguish inheritance, explicit default and finite positive safe integers. Strict readers validate closed requests/responses, all original selector/preview/apply tokens, exact membership and explicit subset, native SHA-256 domain-separated revisions, bounds, all 21 summary fields and historical evidence monotonicity. Rows that fail review remain visible and excluded. The user updates the execution subset explicitly, sees its new ID/revision and confirms that immutable subset before one apply command.

All peer/resource claims are reserved atomically before any notification, then the consumed review, retained attempt and pending owner are installed. A final ownership check follows synchronous subscriber notifications before dispatch. Namespaced attempts never clear each other. Auth, boot, grant, backend, dialog and navigation changes hide data or invalidate reviews but do not clear claims. Unknown apply outcomes permit explicit original-operation status recovery only. Exact durable terminal evidence or conservative durable idle stopped non-dispatch evidence can resolve only its own claim. The W1 local pre-admission revision-conflict exception remains local-only.

The registry is bounded to 80 non-evicting attempts (W1 limit 64; group limit 16), app memory only. It is not a Core-wide, persistent, multi-tab or cross-client replay barrier. Full reload loses it. An explicitly supplied known run ID can restore only that run after full immutable review/request/reducer validation. Keep the displayed run ID before apply. Accepted run IDs are not enumerated by this UI or the new endpoint.

Recovery is explicit. Lost preview or changed-subset replies retain their exact frozen input for one user-triggered retrieval route; there is no automatic retry. `review.current` retrieves the agent’s single current unused review, potentially from another authenticated local client. Its none arm establishes only no unused review, never no historical execution, and cannot release a claim. Recovered reviews remain unconfirmed. Discard sends the exact returned ID through cancel; a concurrently accepted same-ID run may only stop future local admission. Cancel/Stop waiting cannot recall target work or roll back changes.

Local run status remains available with authenticated fresh local ownership while the remote backend is unavailable. Remote refresh uses only an explicit eligible subset of original possibly-dispatched rows and never substitutes current selectors. Historical target outcome/durability, local publication durability, local dispatch, latest observation/sequence/time and admission-stop reasons remain separate. A later failed/weaker observation cannot replace durable historical outcome. Historical all-applied applies only to the execution subset and is not current compliance.

The fixed `useServer` observer chain rechecks authoritative live/generation/auth/state/stale refs after each synchronous owner notification. A recursive auth loss cannot be overwritten by a later owner receiving stale context. Native asynchronous digests and decoders are followed by ownership checks. No selector, grant, run ID, review or evidence is saved in localStorage, URL/history or logs.

Execution must disclose whole-Web typecheck and exact selected synthetic tests, existing Vite React/Tailwind/PNG/jsdom/setup and native binding initialization, ordinary workers, and owned cache/temp/build-info writes. No real Core/provider/listener/browser server is used by these tests. There is no dependency/config change or restoration step.

Remaining original scope: complete remote catalog capability and publication-origin integration, durable file shares, real Core/browser/target workflows, native/race/full CI, actual devices and installed binaries, signed release/provenance and distribution verification. Stale discovery remains nonactionable; generic service navigation uses fresh manual existing review. This group view does not close those acceptance gates.
